# 工作日志

这个博客兼当**每天的工作日志**：一天一条 `content/worklog/YYYY-MM-DD.md`，内容由 `scripts/new-log.mjs` 从当天的 git 提交自动生成草稿，你只需要补「踩的坑 / 今天学到」。

「每天花 20 分钟回忆今天干了啥」是这类习惯最常见的死因，所以这个流程的目标是：**草稿里的东西不用你回忆，git 已经替你写好了；你只补 git 里没有的那部分。**

- 草稿目录：`drafts/`（与 `content/` 平级，**已被 `.gitignore` 忽略**）
- 发布位置：`content/worklog/<日期>.md`
- 脚本：`scripts/new-log.mjs`（等价命令 `pnpm new:log`）
- schema 定义：`content.config.ts` 里的 `worklog` 集合

---

## 1. 每天怎么用

四步，收工前 5 分钟搞定：

```powershell
cd my-blog

# 1) 生成今天的草稿（默认就是本机时区的今天）→ drafts\2026-09-10.md
pnpm new:log

# 2) 打开草稿，补三件事：summary（一句话总结）、坑与解决、今天学到
notepad drafts\2026-09-10.md      # 换成你惯用的编辑器即可

# 3) 发布：自动移动到 content/worklog/ 并把 frontmatter 的 draft 改成 false
pnpm new:log --publish 2026-09-10

# 4) 提交推送（push 之后 CI 自动构建部署）
git add content/worklog/2026-09-10.md
git commit -m "worklog: 2026-09-10"
git push
```

第 3 步做完，草稿就从 `drafts/` 消失了；**不要**再手改产物文件里的 `draft` 字段，那一步脚本已经做掉了。

不带参数时用的日期 = 你机器上今天的日期（本地时区）。晚上 11 点写的日志算今天，不会跑到明天去。

### 命令速查

| 命令 | 作用 |
| --- | --- |
| `pnpm new:log` | 生成今天的草稿 → `drafts/<今天>.md` |
| `pnpm new:log --date 2026-09-09` | 补写某一天（按那一天的时间窗重新采集 git） |
| `pnpm new:log --force` | 草稿已存在时覆盖（会丢掉已写的内容，慎用） |
| `pnpm new:log --dry-run` | 只在屏幕上打印草稿，不写文件 |
| `pnpm new:log --publish 2026-09-10` | 发布：`drafts/2026-09-10.md` → `content/worklog/2026-09-10.md`，并改 `draft: false` |
| `pnpm new:log --publish --force` | 目标文件已存在时强制覆盖（例如已发布过、改完想重发） |
| `pnpm check:drafts` | 守卫：扫 `content/**/*.md`，发现 `draft: true` 就报错（CI 也会跑） |

行为约定（都是实测过的）：

- 草稿已存在且没带 `--force`：**不覆盖**，打印提示，**退出码 0**（这不算错误）；
- 当天没有提交：**正常生成一份空骨架**并打印提示，退出码 0；
- `--publish` 目标已存在且没带 `--force`：**拒绝**，退出码 1（`drafts/` 里的草稿原封不动）；
- `--publish` 时如果 `title` / `summary` 还是占位、或 `pitfalls` / `learned` 还是空的，会打印 `⚠` 提醒但**照样发布**（`title` 为空则直接拒绝，因为空的 `title` 会被 schema 挡下来、让构建失败）；
- 本脚本必须**在仓库根目录**运行（路径按仓库根算，跑错目录会直接报错退出）。

`title` 的初始值是脚本从当天提交里挑的（优先 `feat` / `fix`，同档取标题最长的那个），会被剥掉 `feat:` `fix(blog):` 这类前缀；当天没有提交时是 `（待填）`。其余备选标题放在正文的一条 HTML 注释里，方便你换。

### frontmatter 契约（与 `content.config.ts` 的 `worklog` schema 对齐）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `title` | 字符串 | **必填、不能空**。空了构建会被 schema 拒绝 |
| `date` | 字符串 | `'YYYY-MM-DD'`，与文件名一致 |
| `summary` | 字符串 | **必填**。一句话总结 |
| `tags` | 字符串数组 | 例如 `[部署, 排障]` |
| `project` | 字符串 | 可选。草稿里以 `# project:` 注释形式待命，要填就取消注释 |
| `pitfalls` | 对象数组 | `- problem` / `solution` / `time`（`time` 可选，如 `约 2 小时`） |
| `learned` | 字符串数组 | 一句话一条 |
| `mood` | 数字 1–5 | 可选。草稿里以 `# mood:` 注释形式待命 |
| `draft` | 布尔 | 草稿 `true`，发布后由脚本改成 `false` |

`pitfalls` / `learned` 为空时写 `[]`（不是留空），这样 schema 和以后的聚合脚本都好处理。

## 3. 为什么草稿必须放 `drafts/`，而不能放 `content/` 里写 `draft: true`

这是**实测结论，不是推测**。

`@nuxt/content` 的 `draft` 字段**只挡得住查询，挡不住构建**：

- 页面、列表、sitemap、RSS、llms.txt 这些查询都带 `.where('draft', '=', false)`，所以草稿不会出现在它们里面 —— 看起来是安全的；
- 但 `nuxt generate` 会把**整个内容库**导出成 `/_nuxt_content/blog/sql_dump.txt`（SQLite 的原始导出，gzip + base64），部署到 GitHub Pages 后**任何人匿名访问都能下载**；
- `@nuxt/content` 构建期**没有任何按 `draft` 字段过滤数据库行的逻辑**。实测：临时往 `content/` 里放一篇带唯一标记的 `draft: true` 文章，重新构建后 dump 长度从 **29763 → 30618 字符**，那个标记在 dump 里出现 **3 次**；删掉后恢复原样。

也就是说：**只要 `draft: true` 的文章还在 `content/` 里，它的正文就已经公开了**，`draft: true` 只给了你一种"没发布"的错觉。

另外，`sql_dump.txt` **不能直接删掉**：客户端的内容库（Spotlight 搜索、Finder、终端 `ls`）就靠 `fetchDatabase()` 加载它，删了这些功能全废。

结论：**草稿必须待在 `content/` 之外**，也就是 `drafts/`。工作日志的 `draft` 字段只是为了与 `blog` 集合同构，以及给发布脚本一个明确的开关，**不用它当隐藏开关**。

## 4. 草稿的存放与备份（**已配好私有备份**）

草稿放在 `drafts/`，而 `drafts/` 被主仓库 `.gitignore` 忽略。这一步解决的是「不进构建、不泄露」：

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 草稿放 `drafts/`（已 gitignore） | 永远不会进构建、不会出现在 dump / sitemap / RSS / 网站里 | 单看这一条：只存在本机，硬盘坏了 / 误删就没了 |
| 草稿提交进**主**仓库 | 有远程备份 | **主仓库是 public**：虽然不上网站，但任何人 clone 它、或读 raw 文件就能看到原文 —— 和公开没有实质区别 |

**所以最后的做法是：`drafts/` 本身就是一个独立的、私有的 git 仓库。**

- 目录：`E:\...\my-blog\drafts`（主仓库忽略它，它自己管自己）
- remote：**私有**仓库 `https://github.com/Fiercecoder888/my-blog-drafts`
- 好处：既「不公开」（不在 public 主仓库里），又「有备份」（推到了私有远程）

**备份是自动的**：`scripts/new-log.mjs` 在两步会顺手 `commit + push` 到那个私有仓库 ——
生成草稿后记 `draft: new <日期>`，发布之后记 `draft: publish <日期>`。
推送失败（没网、凭据失效）**只警告不中断**，草稿已经落盘，稍后补一次 `git -C drafts push` 即可。

手改草稿后想立刻备份：

```powershell
git -C drafts add -A
git -C drafts commit -m "draft: 手改内容"
git -C drafts push
```

> ⚠️ 仍然要说清楚：**正式发布进 `content/` 的日志是给全世界看的** —— 它会出现在网站、sitemap、RSS、llms.txt，也会出现在公开的 `sql_dump.txt` 里。别把公司项目名、内部地址、密钥、同事姓名写进去。草稿阶段随便写，**发布前请过一遍**。

## 5. `pitfalls` 为什么要写成结构化的

因为 frontmatter 里的字段是**数据**，正文里的一段文字只是**文本**。

「无限进步」栏目以后要按标签把坑聚合成「坑库」（同一个坑栽过几次、哪类坑最耗时、哪个项目最费劲）—— 这些都要求 `problem` / `solution` / `time` 是能查询、能聚合的字段。写在正文里，聚合脚本只能靠正则去猜，等于永远是死数据。

所以规矩是：

- **结构化那份留在 frontmatter**：`pitfalls`（problem / solution / time）和 `learned`（一句话一条）是唯一权威；
- **正文那份是给人读的**：在「踩的坑与解决」下面把它们展开写，可以加背景、加代码、加截图；
- 以后回头看日志，看正文；以后做「坑库」页面，读 frontmatter。

## 6. 常见问题

**当天没有提交（今天没写代码 / 只改了别的仓库）**

脚本照样生成一份空骨架，正文里写「（2026-09-10 没有 git 提交）」，退出码 0。你可以：
- 手写「今天做了什么」（会议、调研、读文档也算工作）；
- 或者干脆跳过今天 —— 日志断一天不会怎样，**别为了凑数把习惯搞死**。

**要补写前几天**

```powershell
pnpm new:log --date 2026-09-07
```

日期按本机时区解释，git 是拿那一天的时间窗重新查的（前一天 0 点到后一天 23:59 全查出来、再按**你本机时区的日期**精确归类），所以补写和当天写的结果一致。

**误发布了怎么撤回**

把文件**移回** `drafts/`，并把 `draft` 改回 `true`：

```powershell
git mv content\worklog\2026-09-10.md drafts\2026-09-10.md   # 或者手动移动
# 然后编辑 drafts\2026-09-10.md，把 draft: false 改回 draft: true
git commit -m "worklog: 撤回 2026-09-10 草稿"
git push
```

注意：**已经 push 过就意味着正文已经公开过**（而且在 git 历史里）；如果里面误写了敏感信息，移回来只是止血，还得单独处理历史（改内容重新提交、或和托管平台协商）。这也是为什么发布前要过一眼。

**忘了跑守卫脚本？**

`.github/workflows/deploy.yml` 在 `Generate static site` 之前会跑 `pnpm check:drafts`，发现 `content/` 里有 `draft: true` 就报错退出，构建直接被拦下。

**某天的草稿想推倒重来**

`pnpm new:log --date <日期> --force`（会覆盖，先想清楚里面有没有已经写好的内容）。

**一个提交都不想漏**

脚本会把当天的**所有**提交都列出来（包括 `chore:` 这种流水账），你可以删掉不想要的几行。

## 7. 采集口径（脚本到底怎么算的）

只有一次 `git log` 调用（`--pretty` + `--numstat` 一次性拿到 hash / 时间 / 标题 / 父提交 / 逐文件增删），不为每个提交单独调一次 git。

- **时区**：日期和时间一律按**本机时区**算（`--date=format-local:`）。查询窗口左右各放宽一天，再在 JS 里按「本机时区的日期」精确过滤，所以晚上 23:50 的提交算今天，不会漂到明天。
- **多作者 / 不同时区的提交**：按该提交在本机时区显示的日期归类（不是提交自身的 `+0800` 偏移），与你 `git log` 里看到的默认观感一致。
- **合并提交（merge）**：会列出来，但标成「合并提交，git 不给单文件统计」—— git 默认不为 merge 输出 diff，所以它的文件数是 0，这是 git 的正常行为，不是漏采。合并本身带来的改动，算在它两侧的普通提交里。
- **根提交**：加了 `--root`，所以仓库第一个提交的文件清单和增删行数也会被统计到（否则 git 默认不给根提交输出 diff）。
- **二进制文件**：`public/` 下的图片、字体这类会显示成「N 个二进制文件（不计行数）」，它们的增删行数按 0 计，但文件数照算。
- **重命名**：路径按重命名后的新路径归类（`old => new` 会归到 `new` 所在的目录）。
- **空提交**：显示「（无文件改动）」。
- **目录聚合**：按顶层目录统计改动文件数，取 Top 5；仓库根目录下的散文件（如 `package.json`）归到 `(根目录)`。

脚本是纯 Node 实现、零第三方依赖，也不写任何 git 钩子，`drafts/` 不存在时自动创建。
