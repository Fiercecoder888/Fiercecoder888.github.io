## QA 工具做了什么

| 检查 | 方法 |
| --- | --- |
| 控制台 | 捕获 `Runtime.exceptionThrown` / `console.error|warning` |
| 命中测试 | 关键可点元素取中心点 → `document.elementFromPoint` 比对，找出「被别的层盖住」 |
| 裁剪 | 递归向上找最近的 `overflow != visible` 祖先，判断放大的 Dock 图标是否真被裁掉 |
| 横向溢出 | `scrollWidth > innerWidth` |
| 对比度 | CDP 截图 → **自写 PNG 解码（zlib + 反滤波）** → 逐元素采样背景像素；文字色先用 canvas 归一（支持 `oklch`/`color-mix`），**按 alpha 与背景合成**，五点取中位数 |

```bash
node tools/qa.mjs          # 浅色模式
node tools/qa.mjs --dark   # 深色模式
```

## 5. 这 8 项失败的定性（附证据）

### 5.1 开机 3 项 = 测试时序，不是站点缺陷

实测开机时间线（headless、每 500 ms 采样，导航后计时）：

```
+0.8s  ready=loading      boot=0 进度条=0 logo=0 登录页=0
+1.3s  ready=interactive  boot=0 进度条=0 logo=0 登录页=0  Dock=1
+1.8s  ready=interactive  boot=1 进度条=1 logo=1 登录页=0
+4.9s  ready=interactive  boot=1 进度条=1 logo=1 登录页=0
+5.4s  ready=interactive  boot=1 进度条=0 logo=0 登录页=1   ← 3200ms 后切登录页
```

`BootScreen.vue` 的进度条窗口就是 `onMounted` 后 **3200 ms**；而 e2e 是先等 `document.readyState === 'complete'` 再去找进度条 —— 线上图片（2.3 MB 壁纸）没下完时 `readyState` 一直是 `interactive`，等它变成 `complete` 时 3 秒窗口早就过了，于是「未出现进度条 / logo tag=none / 0px」三项一起失败。**同一轮里「登录页出现」「登录后进入桌面」都是 ✔**，说明开机流程本身正常。本地静态服务器上 `readyState` 秒完成，所以同一份产物能 47/47 全绿。

### 5.2 Spotlight / 终端 / Finder 共 5 项 = 客户端内容库冷启动太慢（功能没坏）

代码事实：`SpotlightOverlay.vue`、`TerminalWindow.vue`、`FinderWindow.vue` 都在 setup 顶层 `await useAsyncData(..., queryCollection('blog') ...)`，**数据没到之前整个子树不渲染** —— 这正好解释了「窗口壳在（只有标题『终端』/『Finder』），内容为空」和「Ctrl+K 后连 `[data-spotlight]` 都不出现」。

把等待放大到 45 s 复现（同一个线上地址）：

```
Ctrl+K 后 [data-spotlight] 出现 = true（耗时 24.5s），随后立刻命中 Nuxt（“用 Nuxt 4 + Nuxt Content v3 搭一个博客…”）
终端 ls  → 打出全部 6 篇文章（提交后 3.0s）
终端 whoami → 命中 guest@
Finder → “文章列表 6 项”

```

冷启动要拉两个文件：`_nuxt/sqlite3.BVKGSWc-.wasm`（**864,752 B**，线上 content-type 正常为 `application/wasm`）和 `__nuxt_content/blog/sql_dump.txt`（**12,228 B**，200）。

**定性**：这 5 项不是功能缺失，是 e2e 的 6 s / 0.7 s×4 等待对这条链路太短。但「按下 Ctrl+K 之后最多 24.5 s 里**屏幕上什么都没有**」是真实的体验问题（Suspense 没有 loading 兜底），建议单独记一条待办。
**不确定处**：24.5 s 里网络与 wasm 初始化 / 机器负载各占多少，我没拆开。有一次 CDP 计时显示那次 wasm 请求只花了 91 ms，而面板仍然等了 24.5 s，倾向初始化 / CPU；同一环境下 node 直连拉同一个 wasm 用时 2.3 s–18.9 s，波动极大，所以不足以下定论。

### 5.3 `qa.mjs` 那 3 条「文章页」warn = **本轮未定性**（最需要跟进的一条）

三组证据互相矛盾，如实列出：

- **支持「站点没问题」**：独立直连抓 `/blog/hello-blog`（301 → `/blog/hello-blog/`）→ HTTP 200、**34,266 B**，HTML 源码里 `data-mac-window` / `data-safari-toolbar` / `prose-article` **三个标记都在**。另一次探针在**全新会话里直接打开文章页**时，三个标记也立刻都在（`html=32,367 B`，可见文本是「…你好，这是我的第一篇文章 2026-09-09 随笔约 9 分钟阅读…」）。

**推断（未证实）**：客户端水合时，如果 async 页面（`blog/[...slug].vue` 也是顶层 `await useAsyncData(queryCollection('blog'))`）没能从 payload 立刻拿到数据，Vue 会丢弃 SSR DOM、换成空 fallback → 文章页在内容库就绪前表现为「URL/标题正确、正文全空」。这与 5.2 是同一个根因，也解释了为什么 8 s 不够。**缺口**：我没有在「先开首页 → 再进文章页」这条最像真人的路径上把等待拉到 60 s，也没跑 SPA 点链接的路径（用户叫停后续命令）。
**建议的下一条最小验证**：全新浏览器 → 打开首页 → 点文章卡片（SPA 跳转）→ 轮询 `[data-mac-window]` 最多 60 s；再单独硬刷新一次文章 URL 做对照。**跑完这条之前，既不能说它是真缺陷，也不能说它是抖动。**

# 第十一轮：文章页「15 秒假 404」缺陷的定位与修复（已修复并线上复验）

> 本轮把上一轮留下的「文章页 3 条 warn 未定性」**结案**：那些 warn 不是假阳性，**它们是对的**。

## 1. 现象（线上实测，可重复）

打开一篇正常文章，浏览器里的时间线是：

```
 948 ms   消失   （新文档）
1691 ms   出现   文章正常显示，正文完整
20564 ms  消失   变成自家 404 页：「页面走丢了 你要找的页面不存在，可能已经被移动或删除了」
35903 ms  出现   文章才恢复
```

即：**正常文章会显示约 15 秒的假 404**。工具口径的表现是：`qa.mjs` 文章页 3 条 warn
（找不到 mac 窗口 / 缺少 Safari 工具栏 / 缺少正文容器）、`e2e-desktop.mjs` 线上 8 项失败。

## 2. 定位过程（关键是先造出「能观察时间线」的工具）

1. `tools/live-probe.mjs`：在真浏览器里打开任意 URL，报告关键选择器**首次出现时间**与
   **出现/消失时间线**，并输出关键资源时序。闪空类缺陷只有看时间线才发现得了 ——
   只看「最终有没有」会永远得到「有」。
2. 时间线里的「消失」状态抓到正文是「页面走丢了」，确认消失的不是内容而是**被换成了 404 页**。
3. 资源时序给出决定性证据：

   ```
    1176 ms  /blog/hello-blog/_payload.json   547 ms   4481 B   ← 拿到了 payload
   20132 ms  readyState 变 complete，同时重新请求 _payload.json（0 B）
   24764 ms  /_nuxt/sqlite3.*.wasm         10479 ms  405 KB     ← 内容库 wasm 才开始下载
   35315 ms  /__nuxt_content/blog/sql_dump.txt  305 ms
   ```

## 3. 根因（两层，都已修复）

**第一层（症状）**：`app/pages/blog/[...slug].vue` 里

```js
if (!post.value) throw createError({ statusCode: 404, fatal: true })
```

把「数据此刻拿不到」直接判成「文章不存在」。站点别处（首页/列表/标签）同样用
`queryCollection` 但**不抛错**，所以只有文章页会闪 404 —— 这也解释了为什么只有它报 warn。

**第二层（根因）**：客户端**从来没有复用预渲染 payload**。证据是线上 `_payload.json` 里
`useAsyncData` 的 key 原文：

```
post-\u002Fblog\u002Fhello-blog      →  post-/blog/hello-blog     （无尾斜杠）
```

而 GitHub Pages 会把 `/blog/hello-blog` **301** 成 `/blog/hello-blog/`，于是客户端
`route.path` 带尾斜杠，key 变成 `post-/blog/hello-blog/` —— 与预渲染的 key 永远对不上。
payload 命中不了 → 客户端只能自己去查内容库 → 那是 844 KB 的 WASM SQLite，慢链路上
要 25～35 秒 → 这期间 `post` 为空，被第一层判成 404。

## 4. 修法

- **第一层**：只在服务端（预渲染）判定 404（那时 HTTP 状态码也是 404，SEO 语义正确）；
  客户端把「暂时没数据」交给模板的 `v-if` / `v-else`，显示「正在加载文章…」并给出回列表入口。
- **第二层**：`contentPath` 归一化（解码 + 去掉尾斜杠）后**同时**用于 key 与查询，
  使预渲染与客户端算出同一个 key。

## 5. 修复后线上复验

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 文章页状态切换次数 | 4 次（含 15.3 s 假 404） | **2 次**（1.7 s 出现后不再消失） |
| 文章页是否下载内容库 wasm | 是（10.5 s，405 KB） | **否，完全不再请求** |
| 是否下载 `sql_dump.txt` | 是 | **否** |
| `qa.mjs` 线上 | error 0 / **warn 3** | error 0 / **warn 0**（浅色与深色均 0） |
| `verify.mjs` 线上 | 24 / 0 | 24 / 0 |
| 本地静态产物 | verify 24/0、e2e 48/0、qa 0/0 | 同左（未回归） |

## 6. 顺带取得的两个教训

1. **本地模拟器必须复刻托管商的 URL 规范化**。`tools/serve-static.mjs` 原先不做
   「无尾斜杠 → 301」，于是这个缺陷在本地**永远测不出来**（本机内容库瞬间就绪，
   即使 payload 没命中也是毫秒级）。已补上 301 —— 注意 `Location` 不能再 `encodeURI`
   一遍（`req.url` 已是百分号编码，二次编码会让含中文的路径 404，这条当时真的写错并被
   `verify.mjs` 抓出来了）。
2. **「本地全绿」不等于「线上没问题」**，权威判据是**线上**的浏览器时间线与资源时序。

## 7. 本轮未解决、如实记录

  可见损害（不再有假 404），但说明 Vue 在客户端丢弃/修补了预渲染结果，属于潜在缺陷。

# 第十二轮：自定义光标热点修正（2026-09-18）

## 1. 用户反馈

> 「现在还有点小bug 就是我的这个鼠标箭头和这个✋️ 有点切换不灵敏 做的有点不太好」

## 2. 定位过程（为什么不是靠猜）

先做了两件测量，把「手感」变成数字：

1. `tools/cursor-audit.mjs`（新）在真实浏览器里报告 14 个位置的实际光标 —— **覆盖是对的**：
   该出手型的地方都是手型（`pointer`）、标题栏是箭头、右下角是 `nwse-resize`、终端是十字精度指针。
   所以问题不在「哪块没设光标」，而在**光标自身的锚点**。
2. `scripts/cursor-hotspots.mjs`（新）把 `public/cursors/*.svg` 里内嵌的 PNG 解出来量 alpha 通道，
   并**画出 ASCII 轮廓**（`--art`）看形状朝向。

关键事实：**CSS 里 `cursor: url('/cursors/x.svg')` 不带坐标时，浏览器把热点定在图片左上角 (0,0)**，
而 macos-web 这套图形并不是从左上角起笔的：

| 光标 | 图形实际笔尖/中心 | 不写坐标时的偏移 |
| --- | --- | --- |
| 箭头 `normal-select.svg` | **(3, 2)** | 4 px |
| 手型 `link-select.svg` | **(15, 2)**（食指指尖） | **15 px** |
| I 型 `text-select.svg` | 中心 (16,16) | 14 px |
| 移动 `move.svg` / 十字 `precision-select.svg` / 禁止 `unavailable.svg` | 中心 (16,16) | 14–16 px |
| 缩放类 | 中心 (16,16) | 9–24 px |

**这就是「切换不灵敏」的机制**：箭头按 (3,2) 显示、手型按 (0,0) 显示而它的指尖在 (15,2) ——
指针从箭头换成手型的那一刻，**图形横向跳约 12 px**，视觉上的指尖和真正的触发点错开，
于是「点不准、发飘」。这不是观感问题，是可量化的锚点错位。

## 3. 顺带发现的第二个真缺陷：缩放指针方向错配

画轮廓时发现上游资源的命名与实际朝向**对不上**（`diagonal-resize-1` 的实际形状是 **↖↘**，
`diagonal-resize-2` 是 **↗↙**），而原 CSS 把 `1` 当成水平缩放（ew）用、把 `2` 当成 `nwse` 用：

| 用途 | 原映射 | 实际看到的形状 | 现映射 |
| --- | --- | --- | --- |
| 东/西边框 `ew` | `diagonal-resize-1` | **斜箭头（错）** | `horizontal-resize.svg`（新派生） |
| 东南角 `nwse` | `diagonal-resize-2` | **反向斜箭头（错）** | `diagonal-resize-1` ↖↘ |
| 东北角 `nesw` | **没有规则**（漏） | 退回系统光标 | `diagonal-resize-2` ↗↙（新增规则） |

上游**根本没提供「↔ 水平缩放」这张图**。新增 `scripts/derive-cursors.mjs`：把 `vertical-resize.svg`
的 `<image>` 加 `transform="rotate(-90 16 16)"` 派生 `horizontal-resize.svg`（幂等，可重复执行）。
用 `-90` 而不是 `+90`：渲染后包围盒是 `x2..30`（索引中心正好 16，与热点 `16 16` 对齐；`+90` 会得到 `x1..29`）。

## 4. 一个方法论上的坑：位图分析看不见 SVG 的 `transform`

第一版 `cursor-hotspots.mjs` 只解内嵌位图，于是对**派生的** `horizontal-resize.svg` 报出
「最上像素 (15,2)、图形是竖直的」—— **完全错误的读数**，因为旋转写在 SVG 上、不在位图里。
差点因此把派生方案判成失败。

修法：给工具加 `--render`，用**裸 CDP**（不引 playwright，与本仓库工具链一致）把 SVG 真的画进
`<canvas>` 再 `getImageData` 取 alpha —— 这才是「用户看到的形状」。现在它会检查
「SVG 是否自带 transform」并显式警告位图坐标不可信。

> 教训：**测量工具本身也要被测量。** 同一个工具对 A 类输入正确、对 B 类输入静默给错答案时，

## 6. 巡检工具本身的两个假阳性（顺手修掉）

`cursor-audit.mjs` 原先判「探针点上那个元素」的 cursor，报出 4 个 ✘，全部是探针问题而非光标问题：

| 假阳性 | 真正原因 | 修法 |
| --- | --- | --- |
| Dock 容器背景 = `text` | 探针点 `(left+2, top+2)` 落在 **1.2rem 圆角之外**，根本不在 Dock 形状里，`elementFromPoint` 穿透到下面的文章窗口 | 改用底部内边距带中点 `(left+width/2, bottom-3)` |
| Dock 图标之间的空隙 = `pointer` | 该目标问的是**点上**的光标，我却按「图标元素自身」判 | 按 mode 区分：`center` 判元素自身，`gapRight/edge/blank` 判点命中 |
| 清空桌面按钮 / 文章卡片链接 | 该状态下元素不存在 / 点不在视口内 | 标记为「跳过」，不再算失败 |
| 正文文字 = `pointer` | 点被别的元素盖住 | 覆盖只作为提示打印，不参与判定 |

修完：**12 处全部符合预期 + 2 处合理跳过**，退出码 0。这也说明一件事：
**一个总是红的检查等于没有检查** —— 先把假阳性清干净，它才能在下次真的拦住回归。
