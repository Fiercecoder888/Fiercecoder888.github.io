## 2. 为什么①必须"另外合成"切片（本轮的技术核心）

| 事实 | 出处 |
| --- | --- |
| `queryCollectionSearchSections('blog')` 的切片来自**正文里的小标题**，它只面向 `blog` 集合 | `app/composables/useBlogSearch.ts:166`（原来只调了这一个） |
| 工作日志的「坑 / 收获」写在 **frontmatter**（`pitfalls[].problem`、`solution`、`learned[]`），不在正文里 | `content.config.ts:36-43`、`docs/工作日志.md` §2、§5 |
| **旧索引为什么搜不到日志里的坑/收获**：它只切**正文**（`queryCollectionSearchSections`），而坑/收获写在 frontmatter 里 —— 用已发布的例子说就是：搜 `jsdom` **搜不到 09-11 那天的日志**（`jsdom` 在该文件里只出现在 `pitfalls` / `learned`，即 frontmatter 的 3 处，正文一个字都没提） | 本次实测（口径见 §3.4）：`jsdom` 在 `content/` 下**只命中 09-11 的 frontmatter 3 处**，正文命中 0；`docs/工作日志.md` §5 也写明"结构化那份留在 frontmatter…正文那份是给人读的" |
| **状态说明（防误读）**：上面说的是**旧索引的能力边界**，不是"09-18 的日志已经发布但搜不到"。09-18 那天（光标热点修正）的日志**尚未写**，`content/worklog/` 目前 21 篇、最新 09-17 | 实测：`content/` 全目录搜「光标」**0 命中**（见 §3.4）；等 09-18 的日志发布后，它同样会被索引到 |
| 反例：同一个词能命中**另一半**（正文侧）——`zstd` 在 09-11 既出现在 `pitfalls` 的 solution 里，也出现在正文「今天做了什么」里，所以修好之后它可能同时产出合成切片与正文切片两条结果 | 本次实测：`zstd` 全 `content/` 命中 2 处 —— `2026-09-11.md` 第 25 行（frontmatter）与第 93 行（正文） |

> 说明：上面举例的 `jsdom` / `zstd` 都取自**已发布**的日志（`content/worklog/2026-09-11.md`）。同一轮里修光标热点那件事发生在 09-18，**那天的日志尚未写**（`content/worklog/` 目前 21 篇，最新 09-17），所以现在搜「光标」在整站（含日志）里都搜不到 —— 等 09-18 的日志发布后，它同样会被索引到。

本轮的修法：日志**单独合成**三类切片，和博客切片合并进同一个索引（`useBlogSearch.ts` 的 `buildWorklogSections()`）：

| 切片 | 每篇日志产出 | `title`（结果显示的小标题） | `content`（参与打分 / 摘录） |
| --- | --- | --- | --- |
| 每条坑一片 | `pitfalls.length` 条 | `坑 · <问题截断 46 字>` | problem + solution + 耗时 + Agent |
| 每条收获一片 | `learned.length` 条 | `收获 · <内容截断 46 字>` | 内容 + 「（来自 日期 的日志：标题）」 |
| 整天一片 | 1 条 | `<日期> · <标题>` | summary + project + `#标签` |

整天的 `titles[0]` 统一是「日期 · 标题」，所以结果行第一列永远是**能认出是哪一天**的（日志不像文章有标题，只给 `坑 · …` 会不知道是哪天）。

用现有 21 篇日志算出来的规模（脚本实测，见 §3）：

| 项 | 数量 |
| --- | --- |
| 日志天数（`content/worklog/*.md`） | **21** |
| `pitfalls` 总条数 | **79** → 79 个「坑 · 」切片 |
| `learned` 总条数 | **104** → 104 个「收获 · 」切片 |
| 整天切片 | **21** |
| **合成日志切片合计** | **204** |

另外顺带修掉一个**既有缺陷**：结果标题原先无条件用 `/^.*?\//` 剥前缀，会把「采集 / 去噪 / 归属」这类**正常标题砍掉前半截**。现在改成「只有当标题确实以 `/` 开头（即它是一条路径）时才剥」（`useBlogSearch.ts` 的 `cleanTitle()`）。同一处把 `path` 的兜底从 `??` 改成 `||`，因为空字符串也要走兜底。

### 5.2 ④ 的断言为什么不能只查 `href="/worklog"`

`app/layouts/default.vue` 的**页脚本来就有**一个全局「工作日志」链接，三个进度页都会跟着渲染出来（实测：每页共 **2 个** `href="/worklog"` 链接）。所以「页面上存在指向 `/worklog` 的链接」**在改动之前就是真的** —— 只查裸 `href` 的断言，在「看日志原文 →」被删掉之后**照样是绿的**，等于没加。

所以 `t2` 的断言要求**带测试钩子的那个 `<a>`，且它的 href 正好是 `/worklog`**：

```
record('页面', '无限进步三页 → 日志原文出口', …)
  // 命中条件：/<a[^>]*data-progress-to-worklog[^>]*>/ 里包含 href="/worklog"
  // 三页任一缺失即失败，detail 里点名是哪一页
```

这条与第十二轮 `cursor-audit.mjs` 的教训同源（见 `docs/验收记录.md` §6）：**一个总是绿（或总是红）的检查等于没有检查** —— 先把判据收紧到"只有这轮新加的东西在才算过"。

> **口径声明**：上表左侧的「第十二轮基线」数字来自 `docs/验收记录.md` 第十二轮的实测记录；右侧「本轮实测（t5）」是 **verifier 在冻结产物 + 4180 上串行跑出的原始输出**（本文照抄，未重算）。其中**我本人另外独立复算通过的三条**是 `check:drafts`（27 md / 0 草稿）、`check:leaks`（21 文件 × 19 规则 / 0 命中）、`assets:check`（67 个引用全部 200）—— 这三条是只读脚本，不需要浏览器。

## 8. 之后要加第五个入口时看这里

- **数据来源就一处**：`queryCollection('worklog').where('draft', '=', false).order('date', 'DESC')`。四个入口各写了一次（`useBlogSearch.ts`、`FinderWindow.vue`、`TerminalWindow.vue`），**没有抽公共 composable** —— 这是有意的（每个入口取的字段不同、都是 `useAsyncData` 预渲染），但代价是**口径要手动保持一致**：都过滤了 `draft`，都按 `date DESC`。
- **给自动断言留稳定钩子**：④ 的 `data-progress-to-worklog` 就是给断言用的；①②③ 目前靠可见文案定位（`最近工作日志`、`log <编号|日期|关键词>`），加新入口时**建议同样加 `data-*` 钩子**，否则断言只能绑中文文案，改文案就会红。
- **日志的"可搜内容"来自 frontmatter**：`pitfalls` / `learned` 是唯一权威（`docs/工作日志.md` §5）。合成切片只读 frontmatter —— 只写在正文里的"坑"**不会**产生合成切片（它可能被旧的正文切片命中，但那就回到"搜不到结构化那条"的老问题了）。要给某个词做示例/宣传之前，先按 §3.4 的做法看一眼它在 frontmatter 里有没有命中（本轮就是靠这一步发现界面文案举的「光标」示例整站 0 命中）。要改可搜范围，改 `buildWorklogSections()`，不要去改正文写法。
- **示例词要跟着语料走**：`content/worklog/` 是会天天长的目录（当前 21 篇 / 79 条坑 / 104 条收获），但**界面文案是死的**。加新入口时若要在文案里举例，优先选语料里已验证的宽词（`坑`、`Agent`），或用固定日期（`log 09-17`）而不是易腐的例子。
- 本轮的证据扫描脚本是一次性的，放在 `.tmp/doc-evidence.mjs`（该目录已被 `.gitignore` 忽略）。要把它变成长期回归防线，应该搬进 `tools/` 并挂 `pnpm` script —— **本轮没有搬**，避免和队友的断言改动撞车。
