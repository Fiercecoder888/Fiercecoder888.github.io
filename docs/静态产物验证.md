# 静态产物验证

- 验证对象：`my-blog`（Nuxt 4 博客）执行 `pnpm generate` 后的静态产物
- 验证方式：模拟 GitHub Actions 工作流（`.github/workflows/deploy.yml`）的构建 + 上传前状态
- 验证时间：本次会话
- 验证环境：Windows，Node v24.16.0，pnpm 10.6.4
- 结论摘要：**构建成功，产物体检 100% 通过，13 条主要路径 curl 全部 200**；另发现 1 个"部署形态"层面的风险（见第 6 节问题 1）——**该风险后来真的发生了，并已解决**：仓库一度被命名为 `FierceCoder.github.io`（与账号名 `Fiercecoder888` 不符）而落入项目站形态，最终通过重命名为 `Fiercecoder888.github.io` 规避，零代码改动。详见第 6 节问题 1。

> **后续更新（第 7 节）**：本文第 2–6 节记录的是"HTTP 产物层"的验证（第 5 节第 8 条明确声明"没有在真实浏览器里加载并执行 JS"）。
> 之后补上了浏览器层验收，并且发现 **dev server 通过 ≠ 静态产物通过**——最典型的一例是 `404.html` 在静态产物里是客户端渲染的壳，
> 导致原先"不存在路径"那条断言在静态产物上必然误报失败。**该问题已修复**（检查拆成 HTTP 层 + 浏览器层两条），
> 并新增了模拟 GitHub Pages 的静态服务器与资源引用检查工具，全部命令、工具用法与 2026-09-10 的实测基线见 **第 7 节**。

## 5. 覆盖不到的范围（明确声明）

本次验证是**本机静态产物 + 本地纯静态服务器**层面的验证，以下内容**没有被本次验证覆盖**：

1. **真实 GitHub Pages 的 CDN / 缓存行为**：Pages 走 Fastly CDN，缓存 TTL、`Cache-Control` 由 Pages 决定（本机服务器没有模拟任何缓存头）。首次访问/回源行为、以及"内容更新后多久生效"无法在本机验证。
2. **HTTPS 与 HTTP→HTTPS 跳转**：本机服务器只有 `http://`。混合内容（mixed content）问题、HSTS 行为、证书链均未覆盖。产物内所有资源均为根绝对路径（`/_nuxt/...`），**没有硬编码 http:// 的资源**，这一点只做了源码/HTML 层面的检查，未在 HTTPS 下实测。
3. **自定义域名（CNAME）场景**：本次用 `https://example-user.github.io`。若配置自定义域名，需在 workflow 里把 `NUXT_PUBLIC_SITE_URL` 换成自定义域名并补 `CNAME` 文件；本次**没有**验证 CNAME 文件是否存在于 `public/`（工作流也没有生成它），自定义域名场景完全未覆盖。

**现象**：产物中所有资源引用都是根绝对的，且没有 `<base href>`：

```
<link rel="stylesheet" href="/_nuxt/entry.Bv2SmSWs.css" crossorigin>

```

**证据**：

- `nuxt.config.ts` 中**没有配置 `app.baseURL`**（只有 `runtimeConfig.public.siteUrl`，它只影响 sitemap/rss/canonical 里的绝对地址，不改变资源路径）

- 工作流只把站点地址（现在是 `steps.site.outputs.url`）传给了 `NUXT_PUBLIC_SITE_URL`，**没有**传给 `baseURL`

**影响分析**：

| 部署形态 | 站点地址 | 结果 |
| --- | --- | --- |
| 用户/组织站（仓库名为 `<user>.github.io`） | `https://<user>.github.io/` | ✅ 资源从域名根解析，正常。**本次验证的就是这种形态，13/13 通过** |

1. 把仓库命名为 `<用户名>.github.io`（用户站），保持现状即可；—— **✅ 已采用这一条**（仓库现为 `Fiercecoder888.github.io`，见本节顶部"现状"）
2. 若要按项目站部署，把站点地址和 baseURL 一起改成子路径，例如：

   ```yaml

     id: site
     run: |
       owner=$(echo '${{ github.repository_owner }}' | tr '[:upper:]' '[:lower:]')
       echo "url=https://${owner}.github.io"
       echo "base=/${GITHUB_REPOSITORY#*/}/" >> "$GITHUB_OUTPUT"
   ```

   然后 `NUXT_PUBLIC_SITE_URL: ${{ steps.site.outputs.url }}${{ steps.site.outputs.base }}`、
   `NUXT_APP_BASE_URL: ${{ steps.site.outputs.base }}`，并在 `nuxt.config.ts` 里让它成为 `app.baseURL` 的默认值，
   使资源路径带上 `/my-blog` 前缀。

   > 注意（**已核实**）：**不能再依赖 `${{ steps.pages.outputs.base_path }}` / `${{ steps.pages.outputs.base_url }}`** ——
   > `actions/configure-pages` 已从工作流移除，`steps.pages` 这两个 output **都不存在了**。
   > 移除原因：该 action 即使加 `enablement: true` 也无法创建 Pages 站点，报
   > `HttpError: Resource not accessible by integration`（`POST /repos/{owner}/{repo}/pages` 不在 `GITHUB_TOKEN` 权限内，需要 PAT）。

   > `echo "base=/${{ github.event.repository.name }}/" >> "$GITHUB_OUTPUT"`（或用上面 `$GITHUB_REPOSITORY#*/` 的写法）。
   > 现在工作流的站点地址由一个 `Resolve site url` 步骤按账号名推导（并 `tr` 转小写），详见 7.9 节。

> **诚实标注**：问题 1 的"项目站会坏"结论来自**产物与配置的静态分析**（资源路径形态 + 缺少 `app.baseURL`），

### 问题 3（✅ 已定性为真实泄露，并已加防线）：`__nuxt_content/blog/sql_dump.txt` 会公开整个内容库

**这一节原先是"低，仅记录"，现在要改掉这个定性：它不是"待确认的隐患"，而是实测确认的泄露。**

`/__nuxt_content/blog/sql_dump.txt` 可被匿名访问（线上实测 **200**，体积 **12,220 字节**，见第 3.2 节），它是**整个内容库的原始 SQLite 导出**（gzip + base64），部署到 GitHub Pages 后任何人都能下载。

原来这里写着"对公开博客而言这不算泄密……需要确认草稿会不会被一并 dump 出来"。**这个疑问已经被探针实测回答了，答案是"会"**：

| 实测项 | 结果 |
| --- | --- |
| `@nuxt/content` **构建期**是否按 `draft` 字段过滤数据库行 | **否**。`node_modules/@nuxt/content/dist` 全量 grep 只命中 `draft-07`（JSON Schema 版本号）与 `xxx.draft.md` 文件名约定，没有任何按字段过滤行的逻辑 |
| 查询层的 `.where('draft', '=', false)` 是否挡住页面 / 列表 / sitemap / RSS / llms.txt | **挡得住**（这些查询都带这个条件） |
| 同一个 `draft` 字段是否挡住 dump | **挡不住** |
| 探针：临时放入一篇带唯一标记的 `draft: true` 文章后的 dump 文本长度 | **29,763 → 30,618 字符**，那个唯一标记在 dump 里出现 **3 次** |
| 删除该探针文章后 | 长度恢复原值 |

也就是说：**只要 `draft: true` 的文章还在 `content/` 里，它的完整正文（可能含公司项目名、内部信息）就已经随 dump 公开了**，`draft: true` 只提供了一种"没发布"的错觉。

> **诚实标注**：上表"是否过滤"与"探针长度"两项是**本机探针构建实测**，不是静态推测；探针文件已删除，仓库里没有留下它。
> 探针里的 29,763 / 30,618 是**构建期取到的 dump 文本长度（字符）**，与第 3.2 节线上那份 **12,220 字节的产物文件**不是同一种度量，
> **两者的换算关系未核对**——但这不影响结论：那个唯一标记确实出现在 dump 内容里。
> 另外，"dump 被客户端真正加载"这条消费路径**仍未在浏览器里实测**（仍在第 5 节未验证清单第 9 条上）；
> 本节结论只依赖两件已实测的事：文件可匿名下载、内容是全量导出。

**为什么不能直接把 dump 删掉**：客户端的内容库（Spotlight 搜索、Finder、终端 `ls`）就靠 `@nuxt/content` 的客户端 SQLite WASM 调 `fetchDatabase()` 拉这个文件；删了这些桌面功能全废。所以这必须在**数据源头**上解决，而不是删产物。

**现行对策（已落地）：让未发布的草稿根本不进 `content/`。**

草稿不在 `content/` 里 → 进不了构建 → 不可能出现在 dump、页面、sitemap、RSS 或仓库里。三道防线：

1. **目录约定**：草稿写在仓库根的 `drafts/`，该目录内容被 `.gitignore` 忽略（`draft: true` 写在 `content/` 里是**错的**）。发布 = 把文件**移动**到 `content/blog/`（或以后新增的 `content/worklog/`）并去掉 `draft` 字段。完整工作流见 `drafts/README.md`。
2. **守卫脚本** `scripts/check-drafts.mjs`：扫描 `content/**/*.md` 的 frontmatter，发现 `draft: true`（`'true'` / `"TRUE"` / `yes` / `on` 都识别）或文件名以 `.draft.md` 结尾即**报错退出（exit 1）**，并打印是哪些文件、为什么错、该怎么做。纯 Node 内置模块实现，不引入任何第三方依赖（`import-notes.mjs` 的风格）。
3. **CI 拦截**：`.github/workflows/deploy.yml` 在 `Generate static site` **之前**新增步骤 `Check no drafts in content`（`pnpm check:drafts`），本地忘了跑，构建同样会被拦住。

使用命令：

```powershell
pnpm check:drafts                     # 等价于 node scripts/check-drafts.mjs
move drafts\某草稿.md content\blog\   # 发布：移出 drafts/ 并删掉 draft 字段
```

> **本地已实测，CI 未实测**：守卫脚本在本仓库跑了两种情形——
> `content/` 干净时**通过**（exit 0，输出 `未发现草稿：content 下 6 个 Markdown 文件都没有 draft: true`）；
> 临时放入 `draft: true`、`draft: "TRUE"` 两个探针后**exit 1 并逐个点名**，同时放入的 `draft: false` 文件**没有被误报**，探针文件随后已删除（`git status` 干净）。
> **CI 上那次拦截没有真的跑过**（要 push 才触发，本次没有提交），但它执行的是同一条命令，风险很低。

> **这条防线的边界（未覆盖，如实记录）**：
> ① 它只保证"带 `draft: true` 的草稿不留在 `content/`"，**管不住你把公司内部信息直接写进要发布的内容**——`content/` 里的一切本来就会公开；
> ② 它依赖 frontmatter 里确实写了 `draft: true`；如果一篇未完成稿根本没写这个字段就放进 `content/`，守卫不会知道它"其实是草稿"（这是约定问题，不是脚本能解决的）；
> ③ `drafts/` 被 `.gitignore` 忽略，意味着**草稿只有本地一份、没有远程备份**；要把"不公开"和"有备份"同时拿到，只能另建一个**私有**仓库，取舍与理由见 `drafts/README.md`。

## 7. 补充：为什么必须打在静态产物上（及新增工具与实测基线）

本章写于第 2–6 节之后，补上的正是第 5 节自己声明"未覆盖"的部分，并记录了一类**必须在静态产物上验收才能暴露**的问题。

### 7.1 核心事实：静态产物里的 `404.html` 是客户端渲染的壳

`nuxt generate` 产出的 `.output/public/404.html` 与 `200.html` **是同一份客户端渲染外壳**（本次实测两者均为 **2,701 字节**，字节数完全相同）。它的特征是：

| 检查项 | 实测值 | 含义 |
| --- | --- | --- |
| HTML 里的 `data-ssr="false"` | **存在** | 标记"这份 HTML 没有服务端渲染内容" |
| `<div id="__nuxt"></div>` | **存在且为空** | 只是挂载点，等待浏览器执行 JS 后填充 |
| `<title>` | **不存在** | — |
| 正文里的页面文案 | **不存在** | 连"页面走丢了"都没有；`app/error.vue` 的文案要等浏览器跑完 Nuxt 才出现 |

**关键一点（已证实）**：`/200.html` 与 `/404.html` **都走了 prerender 流程**。
同一次构建（`$env:NUXT_PUBLIC_SITE_URL='https://fiercecoder888.github.io'` + `$env:NODE_OPTIONS='--max-old-space-size=2560'`，`pnpm generate *> .build.log`）里，
Nitro 预渲染路由列表中的原文是：

```
[nitro]   ├─ /200.html (381ms)
[nitro]   ├─ /404.html (381ms)
```

两个文件都在列表里、**耗时还都是 381ms**（同一批），但产物**仍然是那个 SPA 外壳**——
结合上面实测的"两者字节数完全相同、都是 2,701 字节、都带 `data-ssr="false"`"，
结论是：**`/200.html` 与 `/404.html` 都走了 prerender 流程，但产物都是同一份客户端渲染外壳**。
这正是 `nuxt generate` 的设计行为，**不是配置写错，也不用去"修"**。

> 同一次构建的结尾两行是 `[nitro] ℹ Prerendered 57 routes in 5.026 seconds` 与 `[nitro] ✔ Generated public .output/public`。
> 那次产物统计为 181 个文件 / 27 个 HTML / ≈6.01 MB，与第 2.2 节、第 7.5 节的数字一致
> （本次实测的 6,297,765 字节略大，差异来自期间 `TopBar` 等源码改动，两套数字各自都对，不必强行对齐）。

### 7.2 由此产生的真实教训：验收脚本自己会骗人

`tools/verify.mjs` 里"不存在路径"这条检查，过去断言的是 `text.includes('页面走丢了')`。这条断言：

| 环境 | 结果 | 原因 |
| --- | --- | --- |
| dev server（SSR） | ✅ 通过 | SSR 把错误页渲染进 HTML 了 |
| 静态产物 | ❌ **必然误报失败** | 响应正文里根本没有那句文案 |
| 线上（GitHub Pages） | ❌ 同样误报 | 线上跑的就是静态产物 |

后果是：**这个误报同时出现在本地静态产物和线上**，看起来就像"线上部署坏了"，很容易把注意力引到部署上去。
（本次就真的这么走了一遍弯路：先在线上验收，两个不同性质的问题——一个是验收工具自己的 MIME bug，一个是真正的静态行为差异——被混在一起，多花了不少时间才分开。）

**记住这一类坑的形状**：不是站点缺陷，而是**校验脚本断言在了错误的层次上**，且这个错误在 dev server 上恰好被掩盖。

### 7.3 现在的正确做法：分两层断言

| 层 | 工具 | 断言内容 | 为什么在这一层 |
| --- | --- | --- | --- |
| HTTP 层 | `tools/verify.mjs` | ① 状态码必须是 **404**（不能是 200）<br>② 正文必须含 `id="__nuxt"`——证明"服务的是自家 404 页，而不是托管商的默认 404 页" | 这两件事只有 HTTP 响应能回答 |
| 浏览器层 | `tools/e2e-desktop.mjs` | 访问不存在的路径（`/__verify_not_exist__`）后，等 `document.body.innerText` 里出现「页面走丢了」 | 文案是客户端渲染出来的，只有跑完 JS 才存在 |

> 顺带说明：`verify.mjs` 里 `isOurShell` 用的是 `id="__nuxt"` **或** `页面走丢了` 的 or 判断，
> 这样同一份脚本在 dev server（SSR，正文里有文案）和静态产物（SPA 壳，正文里有挂载点）上都能过。
> 但**静态模式的验收必须以静态服务器为准**，见 7.4。

**顺序是有讲究的**：浏览器层的这条用例**必须放在「无 JS 异常」检查之后**。
访问不存在的路径本来就会产生 404 网络日志和 Nuxt 的错误输出，那是**预期行为**；
若把它放在前面，就会污染"无 JS 异常"这条断言。
（`e2e-desktop.mjs` 里除了顺序，还用 `|__verify_not_exist__` 过滤了控制台错误作为第二道保险。）

### 7.4 验收必须用"复刻 GitHub Pages 语义"的静态服务器，不能用 dev server

新工具 `tools/serve-static.mjs`（Node 原生 `http`，无第三方依赖）：

```powershell
node tools/serve-static.mjs [--root .output/public] [--port 4180]
```

它复刻的 GitHub Pages 语义：

| 请求 | 行为 |
| --- | --- |
| `/a/b/` | → `/a/b/index.html` |
| `/a/b` | → `/a/b.html` 或 `/a/b/index.html` |
| `/` | → `/index.html` |
| 找不到 | 返回 `404.html`，**同时 HTTP 状态码是 404**（不是 200） |
| MIME | 正确的 `Content-Type`，其中 **`.wasm` 必须是 `application/wasm`** |

**为什么 `.wasm` 的 MIME 这么重要**：Shiki 的 oniguruma 引擎要按 `application/wasm` 取 wasm，
否则 Chrome 拒绝流式编译，控制台报 `wasm streaming compile failed: ... Expected 'application/wasm'`，
然后回退到 `ArrayBuffer` 实例化。把 `.wasm` 的 MIME 设对前后，`tools/e2e-desktop.mjs` 的「无 JS 异常」检查**从失败变为通过**。

> **诚实标注（这条很有价值）**：这个 MIME 问题**是验收脚本自己的 bug，不是站点缺陷**。
> 它是 7.2 那类坑的第二个实例，而且更隐蔽——报错信息（`Expected 'application/wasm'`）看起来完全像是站点配错了。
> 这正是 7.2 那条教训的意义：验收工具本身也会骗人，看到失败先想清楚"这个断言在哪一层、这个环境对不对"。

### 7.6 新增工具：`tools/asset-check.mjs`（资源引用完整性）

```powershell
node tools/asset-check.mjs [baseUrl] [路径...]     # baseUrl 省略时默认 http://127.0.0.1:4180；默认查 / /blog /about /tags
```

> **2026-09-18 修正**：`assets:check` 这个 script 不传参，而本工具原先**要求**第一个参数是 baseUrl，
> 于是 `pnpm assets:check` 每次都直接打用法说明并以 1 退出（等于这条 script 从来没跑通过）。
> 现已改为：第一个参数不是 `http(s)://` 开头时按「本地静态产物 `http://127.0.0.1:4180`」处理，
> 路径参数顺延。所以两种写法都对：
> `pnpm assets:check`（打本地 4180）、`node tools/asset-check.mjs https://fiercecoder888.github.io / /blog`（打线上）。
> 省略页面参数时用默认的 4 条路径，此时只收集到 67 个引用（该数字随站点演进变化，以实际输出为准）。

作用：把页面 HTML 里引用的**所有**本地资源（`/_nuxt/` 下的 JS/CSS chunk、prefetch / modulepreload、图片等）收集起来，逐个校验是否 200。

**为什么需要它**：静态托管上只要有一个按需加载的 chunk 404，对应组件就会**静默失效**——
页面看起来正常、控制台**也可能不报错**（chunk 根本没被请求到，或者失败被吞了），这种故障靠肉眼极难发现。

这也补上了第 2.4 节的一个短板：那一节是"把 `index.html` 里的 16 个引用拿去和磁盘比对"，
而本工具是**真的逐个发 HTTP 请求**，并且覆盖多个页面（含文章页，会带到文章页才用的 chunk）。
实测本地静态服务器（`.output/public` 由 `serve-static.mjs` 提供）`/ /blog /about /tags /blog/hello-blog` 共收集到 **79 个引用，全部 200**；
线上 `/ /blog /about /tags /blog/hello-blog` 同样是 **79 个引用全部 200**（两边数字一致，说明产物与线上部署内容一致）。

> 访问线上 https 地址时需要 `node --use-system-ca`：本机 hosts 把 github 域名指向 `127.0.0.1` 由 Steam++ 反代，用的是自签证书。

### 7.7 新增 pnpm scripts

`package.json` 里新增（原脚本只有 `dev` / `build` / `generate` / `preview` / `postinstall`，未改动任何依赖版本）：

| script | 展开 | 说明 |
| --- | --- | --- |
| `serve:static` | `node tools/serve-static.mjs` | 起静态服务器（默认 `.output/public`，端口 4180） |
| `verify:static` | `node tools/verify.mjs --base http://127.0.0.1:4180 --skip-comments` | HTTP 层验收 |
| `e2e:static` | `node tools/e2e-desktop.mjs --base http://127.0.0.1:4180` | 浏览器层验收 |

**使用顺序（重要）**：`verify:static` / `e2e:static` / `qa:static` **需要先在另一个终端跑 `serve:static`**
（它们只连 `http://127.0.0.1:4180`，不会自己起服务器）。完整流程：

```powershell

pnpm serve:static              # 2. 另开一个终端，保持运行（4180）

pnpm e2e:static                # 4. 浏览器层验收
pnpm qa:static                 # 5. 视觉体检；深色加 `-- --dark`
pnpm assets:check -- http://127.0.0.1:4180 / /blog /about /tags   # 6. 资源引用完整性
```

### 7.8 通用原则：**dev server 通过 ≠ 静态产物通过**

- 凡是**能用 HTTP 或浏览器验证**的行为，最终验收都要打在**静态产物**上（`pnpm generate` + `serve:static`），**再在线上打一遍**。
- dev server（SSR + HMR）与静态产物（预渲染 HTML + SPA 壳 + 客户端路由）**行为不同**，本文 7.1 的 404 就是最典型的例子。
- **验收工具本身也是被验收对象**：`.wasm` MIME 的 bug（7.4）说明"检查失败"未必等于"站点有问题"。
  遇到失败先分清是**站点缺陷**还是**环境/工具缺陷**，再决定动哪里——这次混在一起，多花了额外时间才分清。
- 顺带记一条工程细节：在 PowerShell 里**不要用管道**（`node ... | Out-File`、`| Select-String`）接 node 的输出，
  会让 node 原生崩溃（`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)`，退出码 `0xC0000409`）。
  用 `> file 2>&1` 重定向、或 `cmd /c "node ... > file 2>&1"`，再读文件即可。

### 7.9 站点地址从哪来：`configure-pages` 已被移除

第 2–6 节成文时，工作流用 `actions/configure-pages` 提供站点地址（`steps.pages.outputs.base_url`）。
**该 action 现在已经彻底移除**——它即使加上 `enablement: true` 也无法创建 Pages 站点，会报
`Resource not accessible by integration`（`POST /repos/{owner}/{repo}/pages` 不属于 `GITHUB_TOKEN` 的权限范围）。
因此 `steps.pages` 这个 output **不再存在**，工作流里凡是指向它的写法都已失效。

现在的真实写法（`.github/workflows/deploy.yml`，构建层）：

```yaml
      - name: Resolve site url
        id: site
        run: echo "url=https://$(echo '${{ github.repository_owner }}' | tr '[:upper:]' '[:lower:]').github.io" >> "$GITHUB_OUTPUT"

      - name: Generate static site
        run: pnpm generate
        env:
          # sitemap / RSS / llms.txt / canonical 都用它
          NUXT_PUBLIC_SITE_URL: ${{ steps.site.outputs.url }}
```

两个必须记住的点：

| 点 | 说明 |
| --- | --- |
| 地址由**账号名推导** | 用户站地址固定是 `https://<账号>.github.io`，所以**不依赖 "Pages 是否已启用"**；build 层即使 Pages 没开也能单独跑通、单独验证（第 7.5 节的基线就是这么来的） |
| **必须转小写** | GitHub Actions 表达式**没有 `toLowerCase`**，所以只能用 shell 的 `tr`。不转的话账号名带大写会生成 `https://Fiercecoder888.github.io`，与 `shared/site.ts` 里的 `url = 'https://fiercecoder888.github.io'` 不一致，canonical / sitemap / RSS 就会写成另一个大小写形态，SEO 上被当成两个 URL |

另外两条与"验证"直接相关的现状：

- **`deploy` 这一步（`actions/deploy-pages@v4`）仍然需要仓库先手动启用 Pages**（Settings → Pages → Source 选 "GitHub Actions"）。
  这是工作流自己开不了的唯一一步；所以"构建能过"和"部署能过"是两件独立的事，本层验收（第 7 章）只覆盖前者。
- 工作流**不需要**再手动补 `.nojekyll` 了，它现在由工作流自己的 `Disable Jekyll` 步骤生成
  （第 2 节那种手工 `New-Item .output/public/.nojekyll` 只是当时复刻该步骤的做法）。
