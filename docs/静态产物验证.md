# 静态产物验证

- 验证对象：`my-blog`（Nuxt 4 博客）执行 `pnpm generate` 后的静态产物
- 验证方式：模拟 GitHub Actions 工作流（`.github/workflows/deploy.yml`）的构建 + 上传前状态
- 验证时间：本次会话
- 验证环境：Windows，Node v24.16.0，pnpm 10.6.4
- 结论摘要：**构建成功，产物体检 100% 通过，13 条主要路径 curl 全部 200**；另发现 1 个"部署形态"层面的风险（见第 6 节问题 1），该风险不影响本次验证的用户站场景，但会影响按项目站部署的场景。

## 5. 覆盖不到的范围（明确声明）

本次验证是**本机静态产物 + 本地纯静态服务器**层面的验证，以下内容**没有被本次验证覆盖**：

1. **真实 GitHub Pages 的 CDN / 缓存行为**：Pages 走 Fastly CDN，缓存 TTL、`Cache-Control` 由 Pages 决定（本机服务器没有模拟任何缓存头）。首次访问/回源行为、以及"内容更新后多久生效"无法在本机验证。
2. **HTTPS 与 HTTP→HTTPS 跳转**：本机服务器只有 `http://`。混合内容（mixed content）问题、HSTS 行为、证书链均未覆盖。产物内所有资源均为根绝对路径（`/_nuxt/...`），**没有硬编码 http:// 的资源**，这一点只做了源码/HTML 层面的检查，未在 HTTPS 下实测。
3. **自定义域名（CNAME）场景**：本次用 `https://example-user.github.io`。若配置自定义域名，需在 workflow 里把 `NUXT_PUBLIC_SITE_URL` 换成自定义域名并补 `CNAME` 文件；本次**没有**验证 CNAME 文件是否存在于 `public/`（工作流也没有生成它），自定义域名场景完全未覆盖。
4. **`actions/configure-pages` 的真实输出值**：本次用固定示例值 `https://example-user.github.io` 代替 `steps.pages.outputs.base_url`。CI 上该值由仓库名/自定义域名决定，真实取值未验证（这正是问题 1 的来源）。
5. **CI 环境差异**：本次在 Node v24.16.0 上构建；工作流用 `node-version: 22`。两个大版本间未做对比。另外工作流的 `pnpm install --no-frozen-lockfile` 也未在本机复刻（本机直接用已有 `node_modules`）。
6. **Jekyll 与 `.nojekyll` 的实际效果**：`.nojekyll` 文件已创建，但"GitHub Pages 是否因它而正确提供 `_nuxt/`"只能在真实 Pages 上确认。本机服务器本来就会提供下划线目录，**无法证伪**。
7. **GitHub Pages 的 404 行为**：本机服务器对未知路径返回裸 `404` 文本；GitHub Pages 会自动用 `404.html` 的内容响应。该差异未在本机复现。
8. **运行时（浏览器）行为**：本次只验证了"能取到文件和状态码"，**没有在真实浏览器里加载并执行 JS**。首屏水合、深色模式切换、桌面 OS 交互、Pinia 状态、客户端路由跳转、`_payload.json` 的实际消费均未验证。
9. **`/__nuxt_content/blog/sql_dump.txt` 的实际消费路径**：文件可访问（200），但客户端是否真的需要它、以及它是否被客户端 SQLite 正常加载，未在浏览器验证。
10. **压缩传输**：本机服务器未启用 gzip/brotli；GitHub Pages 会压缩。真实首屏传输体积未测。
11. **DNS / 部署权限**：`actions/deploy-pages` 是否成功、Pages 环境（`github-pages` environment）审批、部署 URL 均未验证。

## 6. 发现的问题与建议

### 问题 1（重要，建议确认）：产物资源路径是"根绝对路径"，只适合部署在域名根目录

**现象**：产物中所有资源引用都是根绝对的，且没有 `<base href>`：

```
<script type="importmap">{"imports":{"#entry":"/_nuxt/D-n7fN3j.js"}}</script>
<link rel="stylesheet" href="/_nuxt/entry.Bv2SmSWs.css" crossorigin>
<link rel="modulepreload" as="script" crossorigin href="/_nuxt/D-n7fN3j.js">
```

**证据**：

- `nuxt.config.ts` 中**没有配置 `app.baseURL`**（只有 `runtimeConfig.public.siteUrl`，它只影响 sitemap/rss/canonical 里的绝对地址，不改变资源路径）
- `index.html` 中资源路径形如 `/_nuxt/...`（根绝对），且无 `<base href>`
- 工作流只把 `steps.pages.outputs.base_url` 传给了 `NUXT_PUBLIC_SITE_URL`，**没有**传给 `baseURL`

**影响分析**：

| 部署形态 | 站点地址 | 结果 |
| --- | --- | --- |
| 用户/组织站（仓库名为 `<user>.github.io`） | `https://<user>.github.io/` | ✅ 资源从域名根解析，正常。**本次验证的就是这种形态，13/13 通过** |
| 项目站（仓库名如 `my-blog`） | `https://<user>.github.io/my-blog/` | ❌ `/_nuxt/...` 会解析到 `https://<user>.github.io/_nuxt/...`（丢了 `/my-blog` 前缀），**页面 HTML 能打开但 JS/CSS 全部 404，站点不可用**；同时 sitemap/rss 的绝对地址会带上 `/my-blog`，与实际资源路径不一致 |

工作流注释写的是"用户站是 `https://<user>.github.io`"，说明作者预期是用户站。但本仓库名是 `my-blog`，**如果它是按普通仓库发布的，就会落到第二行那种坏情况**。这一点必须确认。

**建议**（二选一）：

1. 把仓库命名为 `<用户名>.github.io`（用户站），保持现状即可；
2. 若要按项目站部署，在工作流里同时设置 baseURL，例如：

   ```yaml
   - name: Generate static site
     run: pnpm generate
     env:
       NUXT_PUBLIC_SITE_URL: ${{ steps.pages.outputs.base_url }}
       NUXT_APP_BASE_URL: ${{ steps.pages.outputs.base_path }}/
   ```

   并在 `nuxt.config.ts` 里让它成为 `app.baseURL` 的默认值，使资源路径带上 `/my-blog` 前缀。

> **诚实标注**：问题 1 的"项目站会坏"结论来自**产物与配置的静态分析**（资源路径形态 + 缺少 `app.baseURL`），**我没有真的按子路径再构建一次来实测**（本机内存有限，且会覆盖已验证的产物）。建议按上述方式在 CI 上验证一次。

### 问题 2（低，提示性）：首屏资源偏大，主要是壁纸

`wallpapers/` 占 2.326 MB（产物 6.01 MB 中的 39%），`app-icons/` 占 0.944 MB，`_nuxt/` 占 1.726 MB（其中 `sqlite3.BVKGSWc-.wasm` 单文件 864.75 KB，gzip 后 405.63 KB，来自 `@nuxt/content` 的客户端 SQLite）。

这不是故障，产物能正常工作，但首次访问的传输量会偏大。若在意首屏：

- 壁纸可考虑按分辨率生成多档并懒加载，或转 WebP/AVIF；
- `app-icons/` 可按需拆分，不必全量预置。

**注意**：`gzip` 后的真实体积未测（本机服务器未启用压缩，GitHub Pages 会压缩），所以实际网络传输量应明显小于 6.01 MB。

### 问题 3（低，仅记录）：`__nuxt_content/blog/sql_dump.txt` 会公开整个内容库

`/__nuxt_content/blog/sql_dump.txt`（12,220 字节）可被匿名访问（200），内容是全部文章的数据库导出。对公开博客而言这不算泄密（文章本来就是公开的），但如果有草稿/未发布内容混在 `content/` 里，需要确认它们不会被一并 dump 出来。本次未逐一核对 dump 内容与已发布文章集合的差异。
