## 0. 先理解三件事，再动手

1. **本项目是纯静态站点。** 在 GitHub Pages 上跑的是「构建时生成好的一堆 HTML/CSS/JS」，
   没有 Node 进程常驻。所有页面在 `pnpm generate` 时就被预渲染成文件：

   ```
   .output/public/
   ├─ index.html
   ├─ blog/index.html
   ├─ tags/index.html
   ├─ about/index.html
   ├─ sitemap.xml      ← 由 server/routes/sitemap.xml.ts 预渲染而成
   ├─ rss.xml          ← 由 server/routes/rss.xml.ts 预渲染而成
   ├─ robots.txt       ← 由 server/routes/robots.txt.ts 预渲染而成
   ├─ llms.txt         ← 由 server/routes/llms.txt.ts 预渲染而成
   ├─ _nuxt/           ← 打包后的 JS / CSS（注意下划线开头，很关键）
   └─ .nojekyll        ← 空文件，禁止 GitHub Pages 跑 Jekyll
   ```

   预渲染的路由清单写在 `nuxt.config.ts` 的 `nitro.prerender.routes` 里。

2. **评论系统在 GitHub Pages 上不可用，这是预期行为。** `/api/comments` 是 Nitro 服务端路由，
   需要 Node 常驻进程，静态托管拿不到。前端 `app/components/BlogComments.vue` 已经做了优雅降级：
   探测到接口 404/405 时显示「当前是**静态部署**（如 GitHub Pages），评论需要 Node 常驻服务，
   所以这里暂时不可用。」——**看到这段黄色提示不是 bug**，是想启用评论请换 Node 托管（见 §5.5）。

3. **工作流已经写好了，你基本不用改代码。** `.github/workflows/deploy.yml` 已经实现
   「推到 main → 自动构建 → 发布到 Pages」，§4 会逐段解释它。

## 1. 两条路线：用户站 vs 项目站（最容易踩坑的地方）

GitHub Pages 有两种站点形态，**仓库名决定了网址里有没有子路径**，而子路径会直接决定本站的
静态资源能不能加载。**第一次部署请直接选「用户站」。**

| 对比项 | **用户站（推荐）** | **项目站** |
| --- | --- | --- |
| 仓库名 | **必须是 `<你的用户名>.github.io`** | 任意，例如 `my-blog` |
| 访问网址 | `https://<用户名>.github.io/` | `https://<用户名>.github.io/my-blog/` |
| 站点根路径 | `/`（就是域名根） | `/my-blog/`（**有子路径**） |
| 本项目需要的改动 | **零改动**，`.github/workflows/deploy.yml` 直接就能用 | **需要额外处理绝对路径**，否则样式/图标/壁纸 404 |
| 每个账号能建几个 | 1 个 | 不限 |
| 适合 | 博客、个人主页的默认选择 | 一个账号放多个项目站，或不想占用那个特殊仓库名 |

### 1.1 用户站：零改动即可

仓库名叫 `<用户名>.github.io`，Pages 会把站点挂在域名根 `/` 上。
本项目所有以 `/` 开头的路径（`/wallpapers/...`、`/app-icons/...`、`/rss.xml`）
**恰好都是对的**，不需要改任何代码。跟着 §2 走就行。

### 1.2 项目站：需要额外处理（重要）

如果仓库叫 `my-blog`，网址变成 `https://<用户名>.github.io/my-blog/`。
但本项目里有大量**以 `/` 开头的绝对路径**，它们会被浏览器解析成
`https://<用户名>.github.io/cursors/...`（**少了 `/my-blog`**），于是全部 404。
经核对，涉及以下位置：

| 位置 | 内容 | 后果 |
| --- | --- | --- |
| `app/configs/wallpapers.ts:19-61` | `background: 'url("/wallpapers/big-sur-1.jpg") ...'` 等 8 张壁纸 | **桌面壁纸整块空白** |
| `app/configs/apps.ts:24-92` | `icon: '/app-icons/finder/128.png'` 等，以及 `to: '/rss.xml'` | Dock / 启动台图标全裂 |
| `app/components/desktop/LaunchpadOverlay.vue:76-89` | `src: '/app-icons/...'`、`to: '/rss.xml'`、`to: '/sitemap.xml'` | 启动台图标全裂、链接点错 |
| `app/layouts/default.vue:21-25` | `<a href="/sitemap.xml">`、`/llms.txt`、`/rss.xml` | 页脚链接 404 |
| `app/pages/index.vue:28-34` | 首页右上角 `/rss.xml`、`/llms.txt`、`/sitemap.xml` | 同上 |
| `app/components/desktop/AboutWindow.vue:48-50` | `/rss.xml`、`/sitemap.xml`、`/llms.txt` | 同上 |
| `app/components/desktop/FinderWindow.vue:140-142` | `window.open('/rss.xml')` 等 | 同上 |
| `app/components/desktop/TopBar.vue:299-315` | `openExternal('/rss.xml')` 等 | 同上 |
| `nuxt.config.ts:40` | `<link rel="alternate" ... href="/rss.xml">` | RSS 自动发现失效 |

**特别注意一个常见误解**：把 `NUXT_PUBLIC_SITE_URL` 设成
`https://<用户名>.github.io/my-blog` 只能修正 `sitemap.xml` / `rss.xml` / `llms.txt` 里
**写在文字里的绝对地址**，上面这些**静态资源请求**和**硬编码链接**它一个都修不好。

> 项目站的正确修法（设置 `app.baseURL`、改用 `useRuntimeConfig().app.baseURL` 拼接、
> 或把 public 资源引用改成相对路径）请见 **`docs/静态托管适配.md`**。
> 本文只负责「用户站零改动」这条路线。

### 1.3 本站真实经历：仓库名错了一个字母，整站白屏

上面这张表不是理论，是本站踩过的一遍：

1. 仓库最初建成了 **`FierceCoder.github.io`**——与真实账号名 `Fiercecoder888` **不一致**，
   而且 `FierceCoder` 其实是**另一个账号**（2017 年注册、0 个仓库），完全不是本人的仓库。
2. 因为仓库名 ≠ `<账号名>.github.io`，Pages 把它当成**项目站**，站点落在
   `https://fiercecoder888.github.io/FierceCoder.github.io/`。于是 `/_nuxt/`、`/wallpapers/`、
   `/app-icons/`、`/rss.xml` 这些以 `/` 开头的请求全都少了一层子路径 → **全部 404 → 页面白屏**
   （HTML 出来了，但没有任何 CSS/JS）。
3. 修法：把仓库**重命名**为 `Fiercecoder888.github.io`（Settings → 仓库名右侧 Rename）。
   改名后：
   - 旧地址会 **301 重定向**到新地址，**仓库内容、提交历史、Actions 历史都保留**；
   - 本地 `git remote` 还指着旧地址，需要手动改一次：
     ```powershell
     git remote set-url origin https://github.com/Fiercecoder888/Fiercecoder888.github.io.git
     git remote -v      # 确认 fetch / push 两行都是新地址
     ```

> **教训**：仓库名必须**与账号名一致**。注意 `FierceCoder` 和 `Fiercecoder888` 差的**不只是大小写**，
> 后半段都不相同——`FierceCoder` 是另一个账号的名字。建仓库前先看一眼浏览器地址栏里
> `github.com/<账号>` 到底是怎么拼的，照抄。
> 建错名字不会立刻报错，它的表现是「部署成功 ✅ 但网页白屏」，很容易误判成构建问题。

## 2. 首次部署完整步骤（用户站路线，照做即可）

> 下文把 `<用户名>` 替换成你的 GitHub 用户名（**区分大小写**，用户名里的字母大小写按 GitHub 地址栏显示的写）。
> 示例：用户名是 `alice`，仓库名就是 `alice.github.io`，网址是 `https://alice.github.io/`。
> **本站**的对应值：用户名 `Fiercecoder888`，仓库名 `Fiercecoder888.github.io`，
> 网址 `https://fiercecoder888.github.io/`。照着填就行。

### 步骤 1：在 GitHub 网页上新建仓库

1. 打开 <https://github.com/new>。
2. **Repository name** 填 **`<用户名>.github.io`**（例如 `alice.github.io`）。
   这是硬性要求——只有这个名字才会被识别成「用户站」，网址里才没有子路径。
3. **Description** 随便写，例如「我的个人博客」。
4. 可见性选 **Public**。
   （私有仓库在免费账号上不能发布 Pages，会卡在 Settings → Pages 里选不到 Source，所以选 Public。）
5. **下面三个复选框全部不要勾**：
   - ❌ Add a README file
   - ❌ Add .gitignore
   - ❌ Choose a license

   原因：本地 `my-blog` 已经是**有提交历史的 git 仓库**了。
   如果远端先有一个 README 提交，两边历史就没有共同祖先，第一次 `git push` 会被拒绝
   （见 §5.6）。
6. 点 **Create repository**。创建完会看到一个「…or push an existing repository from the command line」
   的页面，先用不上，直接看下一步。

### 步骤 2：本地关联远端并推送

在本机打开 PowerShell，执行（把两处 `<用户名>` 换掉）：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog

# 关联远端（本仓库当前没有配置任何 remote，git remote -v 是空的）
git remote add origin https://github.com/<用户名>/<用户名>.github.io.git

# 确认一下当前分支是 main（本仓库默认就是 main）
git branch --show-current

# 首次推送并把本地 main 与远端 main 建立跟踪关系
git push -u origin main
```

- 第一次推送会弹浏览器让你登录 GitHub（Git Credential Manager），或者要求输入 Personal Access Token。
  如果要求密码，**不能用账号密码**，要去 <https://github.com/settings/tokens> 生成一个带 `repo` 权限的
  token 当密码用。
- 如果提示 `error: remote origin already exists`，说明之前加过了，改成：
  ```powershell
  git remote set-url origin https://github.com/<用户名>/<用户名>.github.io.git
  ```
- 推送完成后仓库里应该能看到 `app/`、`content/`、`nuxt.config.ts`、`.github/` 等文件。
  注意 `node_modules/`、`.nuxt/`、`.output/`、`.data/`、`dist/` 已被 `.gitignore` 排除，**不会被推上去**，
  这是对的。

### 步骤 3：把 Pages 的来源切成 GitHub Actions

> ⚠️ **这一步必须人工做一次，工作流自己开不了。** 详见下面的「为什么工作流不能自己开」。
> 状态正确的标志：切完之后 Pages 页面上会显示 **Source = GitHub Actions**（API 里是
> `build_type=workflow`），**不会**再出现分支/目录选择框。

1. 打开仓库页面 → 上方 **Settings** 标签。
2. 左侧栏找到 **Pages**（在「Code and automation」分组下）。
3. **Build and deployment** → **Source** 下拉框，从 `Deploy from a branch` 改成 **`GitHub Actions`**。
4. 不需要选分支、不需要填目录。改完这一步就够了。
   （如果选成了 `Deploy from a branch`，Actions 里部署成功但 Pages 上仍然是空的——这是常见误操作。）
5. 顺手把 **Enforce HTTPS** 勾上（本站已开启）。Pages 首次签发证书要等一会儿，
   刚启用时这个勾可能是灰的，过几分钟再回来勾。

#### 为什么工作流不能自己开 Pages（实测报错）

有人会想让工作流顺手把 Pages 也启用，用 `actions/configure-pages@v5` 加 `enablement: true`。
**实测这条路走不通**，工作流会在这一步红掉，报错文本（来自 check-run 的 annotation）：

```
HttpError: Resource not accessible by integration
Create Pages site failed. Error: Resource not accessible by integration
- https://docs.github.com/rest/pages/pages#create-a-apiname-pages-site
```

原因：启用 Pages 调的是 `POST /repos/{owner}/{repo}/pages`（创建 Pages 站点），
这个接口**不在 `GITHUB_TOKEN` 的权限范围内**，必须用**个人访问令牌（PAT）**才行。

所以本仓库的工作流里**刻意不做这件事**（`configure-pages` 已经移除，改由账号名推导站点地址），
并且 `.github/workflows/deploy.yml` 里写了注释说明原因。看到这段报错不要以为是配置写错了，
它就是「GitHub 不让工作流自己开 Pages」——去 Settings → Pages 手动点一下即可。

### 步骤 4：等 Actions 跑完

1. 点仓库上方 **Actions** 标签。
2. 左侧选 **Deploy to GitHub Pages** 工作流，点最新一次运行（触发器是 `push`）。
3. 你会看到**两个 job**：
   - **build**：安装依赖 → `pnpm generate` → 生成 `.nojekyll` → **打印构建摘要** → 上传产物。
     首次大约 **1.5–3 分钟**（要装 Nuxt 全套依赖 + 下载 better-sqlite3 预编译包）。
   - **deploy**：把上一步的 artifact 发到 Pages，大约 **20–40 秒**。
   合计 **约 2–4 分钟**。两个都变绿 ✅ 才算成功。
4. 如果 `build` 红了，点开失败的那一步看日志，对照 §5 的坑排查（构建/依赖类看 §5.1–§5.3）。
5. 如果 **`build` 绿、只有 `deploy` 红**，先别改代码——这是 Pages 侧的配置/时序问题：
   - 先确认 Pages 是否**真的已启用**、以及**启用时间是否晚于这次运行**（§5.7）；
     首次部署的真实情况就是 `build` 成功、`deploy` 因 Pages 未生效而失败，**再推一次就好了**。
   - 报错里如果是 `Deployment cancelled.`，是被遗留的 `pages build and deployment`
     抢占了 `github-pages` 环境（§5.8）。
   - `build` 绿本身就说明「装依赖 + 构建 + 上传产物」这条链是通的——这正是 §4 开头那个
     「build 层不碰 Pages API」解耦设计的价值。
   - 最快的判断方式：跑一次 `node --use-system-ca tools/gh-status.mjs`（用法见 §7.4）。

> 小提示：推送后如果 Actions 页面几秒钟内没出现新运行，刷新一下页面；
> 也可以在 Actions → Deploy to GitHub Pages → 右侧 **Run workflow** 手动触发一次（工作流里配了 `workflow_dispatch`）。

### 步骤 5：访问站点

浏览器打开：

```
https://<用户名>.github.io/
```

第一次发布后如果还是 404，**等 30–60 秒再刷新**（CDN 生效有延迟）。仍然 404 就回 §5 排查。

## 3. 以后怎么更新

写完文章、改完代码之后，三条命令推上去，剩下的 Actions 自动做：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog
```

- 想只发一次而不改代码：Actions → Deploy to GitHub Pages → **Run workflow**（手动触发）。

## 4. `.github/workflows/deploy.yml` 逐段解释

文件全文 82 行，下面按段落拆开讲。

> **先看整体结构**：push 到 `main` 触发，分两个 job。
>
> - **`build`**：checkout → pnpm 10 → Node 22 → `pnpm install --no-frozen-lockfile`
>   → `pnpm generate` → `touch .output/public/.nojekyll` → 打印构建摘要 → `upload-pages-artifact@v3`
> - **`deploy`**：`actions/deploy-pages@v4`，环境 `github-pages`
>
> **关键设计（踩坑后改出来的）：build 层刻意不碰 Pages API。**
> build 只用 `GITHUB_TOKEN` 能做的事（装依赖、构建、上传产物），站点地址由账号名推导而来，
> 所以**即使 Pages 还没启用，也能单独验证「装依赖 + 构建 + 上传产物」是否成功**——
> 出问题时能一眼分清是「构建坏了」还是「Pages 没开/没配好」。
> 这不是为了好看，是因为第一次部署时 `deploy` 失败、而 `build` 全绿，
> 就是靠这个解耦立刻定位到「Pages 尚未启用」而不是「Nuxt 构建有问题」。

### 4.1 触发条件

```yaml
on:
  push:
    branches: [main]
  workflow_dispatch:
```

- `push.branches: [main]`：只有 **main** 分支收到推送才跑，其他分支不发布。
- `workflow_dispatch:`：允许在 Actions 页面**手动点按钮**触发一次（末尾的冒号不能省，
  空值表示「无参数的手动触发」）。

### 4.2 权限与并发

```yaml
permissions:
  contents: read     # checkout 读代码
  pages: write       # 允许写入 Pages
  id-token: write    # 允许用 OIDC 令牌向 Pages 证明身份（deploy-pages v4 必需）

concurrency:
  group: pages
  cancel-in-progress: true   # 新的发布取消旧的，避免两次部署打架
```

`id-token: write` 是**必须**的：`actions/deploy-pages@v4` 用 OIDC 换取发布凭证。
少了这一行，deploy job 会报权限类错误。`concurrency` 保证 Pages 同一时刻只有一个发布在跑。

### 4.3 build job

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
```

拉取仓库代码到构建机。

```yaml
      - uses: pnpm/action-setup@v4
        with:
          version: 10

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
```

- 装 **pnpm 10** 和 **Node 22**，与本项目要求一致。
- **顺序不能颠倒**：`setup-node` 的 `cache: pnpm` 依赖 pnpm 已经存在；
  如果先 setup-node 后 action-setup，这一步会报「找不到 pnpm 可执行文件」。

```yaml
      # postinstall 会用 scripts/install-sqlite-prebuild.mjs 补 better-sqlite3 预编译包
      - name: Install dependencies
        run: pnpm install --no-frozen-lockfile
```

装依赖。两点说明：

- `--no-frozen-lockfile`：CI 默认会用 `--frozen-lockfile`，一旦 `pnpm-lock.yaml` 和
  `package.json` 有细微不一致就直接失败。这里放宽，允许按 `package.json` 修正锁文件。
- 这一步会顺带跑 `package.json` 里的 **`postinstall`**：
  `node scripts/install-sqlite-prebuild.mjs && nuxt prepare`。
  其中 `install-sqlite-prebuild.mjs` 负责补上 **better-sqlite3** 的预编译二进制
  （Nuxt Content 需要它）。为什么需要这个脚本：pnpm 10 默认**拦截**依赖的 install 脚本
  （`package.json` 的 `pnpm.onlyBuiltDependencies` 只放行了 `esbuild`），
  所以 better-sqlite3 不会自己下载/编译，必须由项目脚本补。
  详见 §5.3。

```yaml
      # 用户站地址固定是 https://<账号>.github.io，仓库名必须也叫 <账号>.github.io。
      # 必须转小写：GitHub 账号名可能带大写（如 Fiercecoder888），但主机名一律小写，
      # 否则 canonical / sitemap / RSS 会写成 https://Fiercecoder888.github.io，
      # 与 shared/site.ts 不一致，SEO 上会被当成两个 URL。
      - name: Resolve site url
        id: site
        run: echo "url=https://$(echo '${{ github.repository_owner }}' | tr '[:upper:]' '[:lower:]').github.io" >> "$GITHUB_OUTPUT"
```

这一步算出**站点地址**，输出到 `steps.site.outputs.url`，后面构建直接用它。
两点必须知道：

- **地址是由账号名推导的**（`github.repository_owner`），不再依赖 `actions/configure-pages`。
  用户站的地址是固定形态 `https://<账号>.github.io`，所以推导得出的值一定正确，
  而且**构建不再依赖「Pages 是否已启用」**——这就是 §2 步骤 3 里那个报错绕开的办法。
- **必须转小写**（这个坑真实发生过，见 §5.9）。GitHub Actions 的表达式**没有**
  `toLowerCase` 函数，所以只能加一步 shell 用 `tr` 转。不转的话会生成
  `https://Fiercecoder888.github.io`（大写 F），而真实主机名是小写，
  canonical / sitemap / RSS 里会写成大写形式，SEO 上被当成两个不同的 URL。

```yaml
      - name: Generate static site
        run: pnpm generate
        env:
          # sitemap / RSS / llms.txt / canonical 都用它
          NUXT_PUBLIC_SITE_URL: ${{ steps.site.outputs.url }}
```

- `pnpm generate` = `nuxt generate`，按 `nuxt.config.ts` 里的
  `nitro.prerender.routes`（`/`、`/about`、`/blog`、`/tags`、`/rss.xml`、`/sitemap.xml`、`/llms.txt`、`/robots.txt`）
  加上所有文章页，生成纯静态文件到 `.output/public`。
- `NUXT_PUBLIC_SITE_URL` 覆盖 `nuxt.config.ts` 里 `runtimeConfig.public.siteUrl` 的默认值
  （`nuxt.config.ts:26` 写的是 `process.env.NUXT_PUBLIC_SITE_URL || SITE.url`，
  即兜底用 `shared/site.ts` 的 `url`）。`server/routes/sitemap.xml.ts`、`rss.xml.ts`、`llms.txt.ts`、
  `robots.txt.ts` 四个路由，以及 `app/app.vue` 的 `<link rel="canonical">`，都读这个值来拼绝对地址。
  **这就是线上 sitemap/RSS/canonical 里不会是 localhost、也不会是大写域名 F 的原因。**

```yaml
      - name: Disable Jekyll
        run: touch .output/public/.nojekyll
```

GitHub Pages 默认会跑 Jekyll 处理站点文件，而 **Jekyll 会忽略所有下划线开头的目录**，
包括 Nuxt 的 `_nuxt/`（里面全是 JS 和 CSS）。放一个空的 `.nojekyll` 文件即可关掉 Jekyll。
少了这一步的现象就是 §5.1：页面能打开但**样式全丢**。

> **`.nojekyll` 是必需的，而且做了双保险**：工作流里这一行 `touch` 是主保险；
> 另外 `public/.nojekyll` 也**提交进了仓库**一份（Nuxt 会把 `public/` 原样拷到产物根目录），
> 万一有人手动上传 `.output/public`、或改工作流时漏掉这一步，也不至于踩 Jekyll 的坑。

```yaml
      - name: Show build summary
        run: |
          echo "产物大小: $(du -sh .output/public | cut -f1)"
          echo "文件数  : $(find .output/public -type f | wc -l)"
          echo "HTML 数 : $(find .output/public -name '*.html' | wc -l)"
          echo "站点地址: ${{ steps.site.outputs.url }}"
```

构建完打印一份摘要，在 Actions 日志里就能直接看到**产物大小 / 文件数 / HTML 数 / 站点地址**。
用处是当「部署绿了但页面不对」时，先看这几个数字是否合理——例如文件数只有几十个、
或者地址里出现了大写，就能立刻断定是构建/地址问题，不用去翻部署日志。

```yaml
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .output/public
```

把 `.output/public` 整个目录打包成 Pages 专用 artifact。**路径必须是 `.output/public`**
（不是 `.output`，也不是 `dist`）。

### 4.4 deploy job

```yaml
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

- `needs: build`：build 失败就不会部署。
- **前提：仓库必须先手动启用 Pages**（Settings → Pages → Source = GitHub Actions，§2 步骤 3）。
  没启用时这一步会失败，报错大意是 Pages 站点不存在（§5.7）。
- `environment.name` **必须**是 `github-pages`，这是 GitHub Pages 的约定环境名；
  写错会导致发布被拒。
- 因为用的是 `github-pages` 这个**共享环境**，它同一时刻只允许一个部署在跑。
  GitHub 在「启用 Pages / 重命名仓库」的瞬间会自己起一条遗留的 `pages build and deployment`
  工作流，也会占住这个环境——两条一起跑会互相取消（§5.8）。
- `url` 会把线上地址显示在仓库首页右侧的 Deployments 里，方便直接点进去。
- `deploy-pages@v4` 消费上一步的 artifact 完成发布。它**不需要**再 checkout 代码，
  也不需要装 Node。

## 5. 常见坑（现象 / 原因 / 解决）

### 5.1 页面能打开，但样式和脚本全丢（白底黑字、布局塌掉）

**现象**：HTML 能出来，但 `https://<用户名>.github.io/_nuxt/xxx.js`、`_nuxt/xxx.css` 全是 **404**，
浏览器控制台一堆 404，页面没有任何样式。

**原因**：GitHub Pages 默认启用了 Jekyll，而 Jekyll 会跳过下划线开头的目录，`_nuxt/` 整个被吞掉。

**解决**：
- 走 Actions 工作流的话，**正常情况下不会出现**——工作流里已有
  `- name: Disable Jekyll / run: touch .output/public/.nojekyll`。
  先确认这一步确实执行成功了（Actions 日志里能看到）。
- 如果你是**手动**把 `.output/public` 上传/推到 Pages 分支，一定要自己造这个文件。
  Windows PowerShell 里 `touch` 不存在，用：
  ```powershell
  New-Item -ItemType File -Force .output\public\.nojekyll | Out-Null
  ```
- 顺手确认产物目录里确实有这个文件：
  ```powershell
  Test-Path .output\public\.nojekyll     # 期望输出 True
  ```
- 浏览器打开 `https://<用户名>.github.io/_nuxt/` 下任意一个真实文件 URL，能下载就说明修好了。

### 5.2 `sitemap.xml` / `rss.xml` 里还是 `http://localhost:3000`

**现象**：打开 `https://<用户名>.github.io/sitemap.xml`，里面 `<loc>` 是
`http://localhost:3000/...`；RSS 的 `<link>` 同理。搜索引擎会把这些地址当成站点地址，收录直接废掉。
（同一个毛病的其他表现：地址写成**大写账号名** `https://Fiercecoder888.github.io`（§5.9），
或者干脆是空地址——都是「构建时拿到的站点地址不对」这一类问题。）

**原因**：构建时没注入 `NUXT_PUBLIC_SITE_URL`，于是用了 `nuxt.config.ts:26`
`runtimeConfig.public.siteUrl` 的兜底值 `SITE.url`（`shared/site.ts` 里的 `url`）。

**解决**：
1. 确认 `.github/workflows/deploy.yml` 的 `Generate static site` 这一步带着：
   ```yaml
   env:
     NUXT_PUBLIC_SITE_URL: ${{ steps.site.outputs.url }}
   ```
   这一行丢了是最常见的原因（尤其手抄工作流时）。
   （**注意**：早期版本这里写的是 `${{ steps.pages.outputs.base_url }}`，靠
   `actions/configure-pages` 提供；那个 action 已经移除，现在由工作流自己的
   `Resolve site url` 步骤推导，**仍然必须是转成小写的地址**，见 §5.9。）
2. 确认地址**是小写**。若 sitemap 里出现 `https://Fiercecoder888.github.io`（大写 F），
   说明 `Resolve site url` 那一步的 `tr '[:upper:]' '[:lower:]'` 丢了或没生效（§5.9）。
3. 改完后**重新触发一次构建**（重新 push，或 Actions 页面 Run workflow），
   本地改文件不算——Pages 上的文件是构建产物。
4. 有缓存的话强制刷新（Ctrl+F5）再检查。

> **关于 `shared/site.ts` 的 `url` 字段——旧说法已作废**：本文早前写过「当前代码里没有任何地方
> 引用 `SITE.url`，只改它是没用的」。**这句现在不成立**：`nuxt.config.ts:26` 就是
> `siteUrl: process.env.NUXT_PUBLIC_SITE_URL || SITE.url`，即 `SITE.url` 是**兜底值**。
> 现状：
>
> - `shared/site.ts` 的 `url` 已经是真实域名 `https://fiercecoder888.github.io`（小写）；
> - CI 构建时它会被 `NUXT_PUBLIC_SITE_URL` 覆盖，所以**线上以注入值为准**；
> - 它影响的是「没有注入环境变量」的场合：本地 `pnpm generate`、或换到别的静态托管。
>   这四个 SEO 路由在 `config.public.siteUrl` 取不到值时会写出空地址，所以
>   **`SITE.url` 应该一直保持等于线上真实地址（小写）**，别留成模板里的占位值。

### 5.3 Actions 里 `pnpm install` 失败在 better-sqlite3

**现象**：`Install dependencies` 这一步红了，日志里有
`[sqlite-prebuild] 所有镜像均下载失败。` 或者 `node-gyp` / `gyp ERR!` 之类的编译报错。

**原因**：Nuxt Content 依赖 **better-sqlite3**（原生模块）。它的正常安装需要下载预编译二进制或本地编译：

- pnpm 10 **默认拦截依赖的 install 脚本**，better-sqlite3 自己那套 `prebuild-install` 不会跑；
- 项目 `package.json` 的 `pnpm.onlyBuiltDependencies` 只放行了 `esbuild`；
- 所以本项目用 `scripts/install-sqlite-prebuild.mjs` 手动补二进制（挂在 `postinstall` 里）。

**解决**：
1. 打开 `scripts/install-sqlite-prebuild.mjs`，看第 35–40 行的**镜像列表**（按顺序尝试，第一个成功即停）：
   ```
   https://registry.npmmirror.com/-/binary/better-sqlite3/v<版本>/better-sqlite3-v<版本>-node-v<ABI>-linux-x64.tar.gz
   https://ghfast.top/https://github.com/WiseLibs/better-sqlite3/releases/download/v<版本>/<同上文件名>
   https://gh-proxy.com/https://github.com/WiseLibs/better-sqlite3/releases/download/v<版本>/<同上文件名>
   https://github.com/WiseLibs/better-sqlite3/releases/download/v<版本>/<同上文件名>
   ```
   四个全挂才会整体失败。日志里会逐个打印 `[sqlite-prebuild] 尝试：<url>` 和失败原因，看哪个报什么。
2. 注意脚本是**幂等**的：`node_modules/better-sqlite3/build/Release/better_sqlite3.node` 已存在就直接跳过。
   GitHub Actions 每次都是干净环境，所以 CI 上每次都会真下载；本地卡住时可以删掉那个 `.node` 文件重试。
3. 常见具体原因：
   - **文件名的 ABI / 平台对不上**：asset 名由 `process.versions.modules`（ABI）、
     `process.platform`、`process.arch` 拼出来。Actions 上是 Node 22 + linux + x64，
     而 npmmirror 上不一定每个版本都齐全 → 会自动落到 ghfast / gh-proxy 镜像，属正常。
   - **镜像临时不可用**：换个时间重跑（Actions 页面 → 失败运行右上角 **Re-run failed jobs**），
     或者临时把可用的镜像 URL 提到 `mirrors` 数组第一位。
   - **升级了 better-sqlite3 版本**：确认 `pnpm-lock.yaml` 和 `package.json` 里的版本一致，
     否则拼出来的文件名在镜像上不存在。
4. **兜底方案**（脚本自己也会提示）：手动下载那个 `better-sqlite3-v<版本>-node-v<ABI>-linux-x64.tar.gz`，
   解压后把里面的 `build/Release/better_sqlite3.node` 放到
   `node_modules/better-sqlite3/build/Release/` 下。
   ⚠️ 注意 CI 是 Linux，本地 Windows 下好的是 `win32-x64` 的版本，
   **两者不能互换**，也不要把本地的 `.node` 提交进仓库。
5. 想彻底绕开这个原生依赖，只能不用 Nuxt Content 的 SQLite 后端（代价很大），
   本项目不建议走这条路。

### 5.4 图片 / 壁纸 / Dock 图标 404（项目站专属）

**现象**：页面结构正确，但桌面背景是纯色、Dock 和启动台图标是裂图，
控制台是 `https://<用户名>.github.io/wallpapers/big-sur-1.jpg 404`（注意**没有** `/my-blog` 这一段）。

**原因**：仓库名不是 `<用户名>.github.io`，站点被挂在子路径 `/my-blog/` 下，
而本站 CSS 和组件里用的是以 `/` 开头的**根路径绝对地址**。清单见 §1.2 的表格。

**解决**：
1. **最省事的办法**：这条路线别用，改建成用户站（仓库名 `<用户名>.github.io`），零改动。
2. 真要发布项目站，按 `docs/静态托管适配.md` 处理：
   给 Nuxt 设置 `app.baseURL`，并把 `app/assets/css/main.css`、`app/configs/wallpapers.ts`、
   `app/configs/apps.ts`、`app/components/desktop/LaunchpadOverlay.vue`、
   `app/layouts/default.vue`、`app/pages/index.vue`、`app/components/desktop/AboutWindow.vue`、
   `app/components/desktop/FinderWindow.vue`、`app/components/desktop/TopBar.vue`
   里那些 `/...` 硬编码统一改成基于 baseURL 的写法。
3. 提醒：**光把 `NUXT_PUBLIC_SITE_URL` 改成带 `/my-blog` 的地址是不够的**，
   它只影响 sitemap/RSS/llms.txt 的文本内容，修不了资源请求。

### 5.5 评论区显示「当前是静态部署…」

**现象**：文章页底部有一块黄色提示：
「当前是**静态部署**（如 GitHub Pages），评论需要 Node 常驻服务，所以这里暂时不可用。」

**原因**：**这是预期行为，不是 bug。** 评论功能由 `server/api/comments/*`（GET / POST / DELETE）
提供，还依赖 `server/utils/comments-db.ts` 里的 SQLite 数据库文件，必须有 Node 进程常驻才能工作。
GitHub Pages 只能托管静态文件，`/api/comments` 请求会返回 404/405，
`app/components/BlogComments.vue` 捕获到这个状态后就把表单换成说明文案（`apiUnavailable` 分支）。

**解决**：
- 接受它（博客本身完全可用），或者
- 想启用评论就换成**支持 Node 运行时的托管**，例如 Cloudflare Workers/Pages Functions、Vercel、
  Netlify Functions、Railway、或者自己的 VPS。
  这条路要改的是「部署形态」而不是本文的 Pages 流程：不再跑 `pnpm generate`，
  而是跑 `pnpm build` 并保留 `.output/server`，同时注意 SQLite 文件需要**持久磁盘**
  （多数 Serverless 平台的临时文件系统会在实例重启后丢掉评论数据，需要挂载卷或换用外部数据库）。
  具体 API 设计见 `docs/评论系统.md`。
- **不要**为了消除这块提示去删组件代码，否则以后想换托管时还得写回来。

### 5.6 `git push` 被拒绝（rejected / 无共同祖先）

**现象**：第一次推送时出现下面这类报错：

```
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/<用户名>/<用户名>.github.io.git'
hint: Updates were rejected because the remote contains work that you do not have locally.
```

或者：

```
fatal: refusing to merge unrelated histories
```

**原因**：建仓库时勾了 **Add a README file**（或 .gitignore / license），
GitHub 先建了一个提交，远端有了本地没有的历史；
而本地 `my-blog` 是独立初始化的仓库，两边没有共同祖先。

**解决**（按推荐顺序）：

1. **推荐：把远端的历史接上来，再推**——先拉取并用 rebase 把本地提交放到远端提交之后：
   ```powershell
   git pull --rebase origin main
   git push -u origin main
   ```
   因为两边改的文件基本不重叠（远端只有一个 README），一般不会冲突。
2. **如果 `git pull --rebase` 报 `refusing to merge unrelated histories`**：
   ```powershell
   git pull --rebase origin main --allow-unrelated-histories
   git push -u origin main
   ```
3. **如果只是「远端被别处改过、本地落后」**（比如在另一台电脑推过），
   同上，先 `git pull --rebase origin main` 再 `git push`，**不要**用 `-f`。
4. **最后的办法：强推覆盖远端**——只有在你**确定远端那些提交毫无价值**时才用：
   ```powershell
   git push -f origin main
   ```
   ⚠️ **风险很大**：`-f` 会**永久丢弃远端上本地没有的提交**，无法通过普通 `git pull` 找回
   （只能在 GitHub 的 Activity / 悬空提交里碰运气）。如果那个仓库里已经有别人推的东西、
   或者你已经在网页上改过文件，**不要用 `-f`**。
   更安全的做法是去 GitHub 网页把那个多余的 README 删掉（删文件提交），再 `git push`。

### 5.7 `deploy` 失败：Pages 还没启用（或启用得比这次运行晚）

**现象**：`build` job 全绿 ✅，`deploy` job 红 ❌，失败信息指向 **Pages 未启用 / 站点不存在**
（不是编译或依赖报错）。

**原因**：这类失败几乎都是「**Pages 尚未启用**」，或者**这一次 workflow 运行跑的时机比
「Pages 被切到 GitHub Actions」还早了几秒**——第 1 次运行就是这种情况（build 成功、deploy 失败），
Pages 启用后**再推一次就成功了**。

> 为什么会出现「差几秒」：`deploy` 用的是 `github-pages` 环境，环境/站点是平台侧的配置，
> 和 workflow 触发是两个独立时间线。你在 Settings 里刚点完 Source，事情可能还没生效，
> 而 push 触发的构建已经在跑了。

**排查步骤（按顺序做，别急着改代码）**：

1. **先确认 Pages 真的开了、以及它是几点开的**：
   仓库 → Settings → Pages → 看 **Source 是不是 `GitHub Actions`**；
   再看 Actions 页面这次运行的**开始时间**，跟 Pages 启用时间比一下。
   如果运行早于启用，那这次失败是**预期内的**，不需要改任何东西。
2. **跑一下状态脚本**（它会把「Pages 是否启用 + 最近几次运行」一次列出来）：
   ```powershell
   cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog
   node --use-system-ca tools/gh-status.mjs
   ```
3. **确认 build 层是好的**。因为 build 层刻意不碰 Pages API（见 §4 开头），
   build 全绿 + deploy 失败 ⇒ **构建和产物没问题**，问题 100% 在 Pages 侧配置。
4. **再推一次**（或 Actions → Run workflow 手动触发）。启用生效后就会变绿。
5. 仍然失败再看 §5.8（环境被遗留任务占住）和 §4.4 的 `environment.name` 是否写成
   `github-pages`（写错会直接被拒）。

### 5.8 遗留的 `pages build and deployment` 占住 `github-pages` 环境 → `Deployment cancelled.`

**现象**：Actions 列表里除了自己的 **Deploy to GitHub Pages**，还多出一条名为
**`pages build and deployment`** 的工作流；自己的部署偶发失败，报 **`Deployment cancelled.`**。

**原因**：GitHub 在**「启用 Pages」或「重命名仓库」的那一瞬间**，会自动起一条**遗留（legacy）的
Jekyll 工作流** `pages build and deployment`。这条工作流：

- 把**仓库根目录**当成 Jekyll 站点来构建（本站实测这次构建的产物是 **3.50 MB**，
  和真正该发布的 `.output/public` 完全是两码事）；
- 占用 `github-pages` 这个**共享环境**。而该环境同一时刻只允许一个部署在跑。

所以如果此时你去**取消它**，会把同一环境里**正在飞的自己的部署一起取消**，
报 `Deployment cancelled.`——**取消别人的部署，结果取消了自己**。

**解决**：

1. **正确做法：等它自己跑完**（通常一两分钟），或者
2. 如果你确实要取消它，**先取消它、确认 `github-pages` 环境空闲了，再触发自己的部署**
   （顺序反了就会互相取消）。
3. 之后触发自己的部署：重新 `git push`，或 Actions → Deploy to GitHub Pages → **Run workflow**。
4. 别去删这条遗留工作流（它不是仓库里的文件，删不掉），它只会在启用 Pages / 改名那一刻出现一次；
   它跑完之后就只剩你自己的那条了。
5. 确认线上到底是哪条工作流赢的：用 §7.4 的 `gh-deploy-watch.mjs` 看自己的 run，
   它跑完会去探测线上是否真的上线。

> 判断依据：如果 artifact 大小是 **3.50 MB 左右**、而且构建步骤里有 Jekyll 字样，
> 那就是这条遗留工作流；本站真正的产物是 **181 个文件 / 6.01 MB / 27 个 HTML**（§7.1）。

### 5.9 站点地址带了大写账号名（`https://Fiercecoder888.github.io`）

**现象**：sitemap / RSS / canonical 里的地址是大写形式 `https://Fiercecoder888.github.io`，
而浏览器地址栏里实际是 `https://fiercecoder888.github.io`。

**原因**：账号名是 `Fiercecoder888`（首字母大写 F），而**主机名不区分大小写、规范写法一律小写**。
如果直接用表达式把 `github.repository_owner` 拼进 URL，就会得到大写形式。
**GitHub Actions 的表达式没有 `toLowerCase` 函数**，只能加一步 shell 用 `tr` 转：

```yaml
      - name: Resolve site url
        id: site
        run: echo "url=https://$(echo '${{ github.repository_owner }}' | tr '[:upper:]' '[:lower:]').github.io" >> "$GITHUB_OUTPUT"
```

**解决**：

1. 确认工作流里有上面这一步，并且 `NUXT_PUBLIC_SITE_URL` 取的是 `${{ steps.site.outputs.url }}`。
2. 确认 `shared/site.ts` 的 `url` 也是**小写**（`https://fiercecoder888.github.io`）。
3. 触发一次构建，然后打开线上 `/sitemap.xml` 搜一下有没有大写形式：
   ```powershell
   $u = 'https://fiercecoder888.github.io'
   (Invoke-WebRequest "$u/sitemap.xml").Content -split "`n" | Select-String 'github.io' | Select-Object -First 5
   ```
   期望：全部是小写。
4. **为什么必须修**：canonical / sitemap / RSS 写成大写形式，等于告诉搜索引擎
   「另有一个叫 `Fiercecoder888.github.io` 的站点」，同一个页面被当成两个 URL，
   收录和权重会分散。这个坑**真实发生过**，是 `fix(ci): 站点地址转小写` 那次提交修掉的。

## 6. 自定义域名（可选）

已经有域名（例如 `blog.example.com`）的话，可以不用 `*.github.io` 地址。

### 6.1 在项目里加 CNAME 文件

Nuxt 会把 `public/` 目录下的内容**原样拷到产物根目录**，所以文件放这里：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog
Set-Content -Path public\CNAME -Value 'blog.example.com' -NoNewline
```

- 内容就是**裸域名**，一行，不要写 `https://`、不要写路径、结尾不要有多余空行。
- 该文件必须进 Git（`public/` 没被 `.gitignore` 排除）：
  ```powershell
  git add public/CNAME
  git commit -m "chore: 添加自定义域名 CNAME"
  git push
  ```
- 为什么用 `public/CNAME` 而不是在 Pages 设置里让 GitHub 自动写：走 **Actions 发布**时，
  artifact 里是什么就发布什么；GitHub 自动建的那份 CNAME 不一定能保住。放进仓库最可靠。

### 6.2 在 GitHub 上填自定义域名

1. 仓库 → **Settings** → **Pages** → **Custom domain** 填 `blog.example.com` → **Save**。
2. GitHub 会做一次 DNS 检查。刚加完报「DNS check unsuccessful」是正常的，
   等 DNS 生效（几分钟到几小时）后回来点 **Check again**。
3. 等证书签发完成后，勾上 **Enforce HTTPS**（强制 HTTPS）。证书签发可能要几分钟到几小时。

### 6.3 在域名商那里加 DNS 记录

| 你要用的域名 | 记录类型 | 主机名 / 名称 | 值 |
| --- | --- | --- | --- |
| 子域名，如 `blog.example.com` | **CNAME** | `blog` | `<用户名>.github.io` |
| 裸域名（apex），如 `example.com` | **A** | `@` | `185.199.108.153`<br>`185.199.109.153`<br>`185.199.110.153`<br>`185.199.111.153` |

- CNAME 的值**不要**带 `https://`，也**不要**带仓库名，最后不要加 `.`（多数面板会自动补）。
- 裸域名用 A 记录是 GitHub Pages 的官方做法；如果你的域名商支持 `ALIAS` / `ANAME`，
  也可以指向 `<用户名>.github.io`。**具体 IP 以 GitHub 官方文档为准**，
  它们偶尔会调整，部署前建议核对一遍。
- DNS 改完可以用下面命令确认解析是否生效：
  ```powershell
  Resolve-DnsName blog.example.com -Type CNAME
  ```

### 6.4 把 `NUXT_PUBLIC_SITE_URL` 改成自定义域名

**这一步不做的话，sitemap / RSS / llms.txt 里仍然是 `*.github.io` 地址**，
和实际访问的域名不一致，对 SEO 不利。

在 `.github/workflows/deploy.yml` 的 `Generate static site` 步骤里改成硬编码：

```yaml
      - name: Generate static site
        run: pnpm generate
        env:
          NUXT_PUBLIC_SITE_URL: https://blog.example.com
```

说明：
- **不要**写成 `https://blog.example.com/`（结尾带斜杠）。四个 SEO 路由里有
  `.replace(/\/$/, '')` 处理，多一个斜杠通常不会出错，但统一不带斜杠更稳。
- 现在的 `Resolve site url` 步骤是**按账号名推导**用户站地址的
  （`https://<账号>.github.io`），它**不知道**你配了自定义域名（早期用的
  `actions/configure-pages` 才会去问 Pages 站点，那个 action 已经移除，见 §2 步骤 3 与 §4.3）。
  所以**配置了自定义域名就必须像上面这样硬编码**，否则 sitemap / RSS / canonical 里
  仍然写 `*.github.io`。
- 改完 push 一次，等 Actions 跑完，再按 §7 复检 sitemap/RSS。
- 换域名后，搜索引擎那边等于一个新站点，需要**在 Google Search Console 里重新添加并提交 sitemap**（见 §7）。

仓库里新增了两个查 GitHub 状态的脚本。**两个都必须加 `--use-system-ca`**，原因见下。

#### `tools/gh-status.mjs` —— 一眼看清仓库 / 站点类型 / Pages / Actions

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog
node --use-system-ca tools/gh-status.mjs                    # 默认查 origin 指向的仓库
node --use-system-ca tools/gh-status.mjs Fiercecoder888/Fiercecoder888.github.io
```

它一次打印：

- **仓库信息**：名字、默认分支、可见性；
- **站点类型判定**：仓库名是否等于 `<账号名>.github.io` → 是**用户站**（地址无子路径）
  还是**项目站**（地址多一层子路径，会白屏，见 §1）；
- **Pages 是否启用**、`build_type` 是不是 `workflow`（`null` = 还没启用，见 §5.7）；
- **最近几次 Actions 运行**：编号 / 提交 / 结论；
- **失败时自动拉 check-run 的 annotation**，把真正的报错文本打出来
  （例如 §2 步骤 3 里那个 `Resource not accessible by integration`，就是在这一步被抓出来的）。

#### `tools/gh-deploy-watch.mjs` —— 等部署跑完并探测线上是否真的上线

```powershell
node --use-system-ca tools/gh-deploy-watch.mjs            # 等最新一次运行
node --use-system-ca tools/gh-deploy-watch.mjs 8787cc3    # 等指定提交那次（sha 前缀即可）
node --use-system-ca tools/gh-deploy-watch.mjs --site https://fiercecoder888.github.io/
```

它会：

1. 找到对应的 workflow run（找不到就每 5 秒重试）；
2. **等它跑完**，逐轮打印状态，结束后**打印每个 job 的步骤结果**；
3. 有失败就打印**失败步骤的 annotation**（真正的报错原因）；
4. 然后**探测线上**是否真的上线：抽查 `/_nuxt/` 资源、壁纸、以及
   `/sitemap.xml`、`/rss.xml`、`/llms.txt`、`/robots.txt` 这些 SEO 文件。

> **部署绿了 ≠ 网站好了**：`deploy` job 成功只说明 artifact 发出去了，
> 站点可能因为「仓库名不是用户站」「地址大写」而表现异常。所以这个脚本最后那步线上探测很有价值——
> 它是「部署成功」到「用户真的能打开」之间的那道验证。

#### 为什么必须加 `--use-system-ca`

本机 hosts 把 **`github.com` / `api.github.com` 指向了 `127.0.0.1`**，由 **Steam++ 加速器**
（监听 `0.0.0.0:443`）做反代，而它的证书是**自签的**——Node 内置的 CA 列表不认，
不加 `--use-system-ca` 就会报证书校验失败（`unable to verify the first certificate` 之类）。
加上这个开关后，Node 改用**系统证书库**，就正常了。

**另一个实战经验**：

- **GitHub Actions 的日志下载需要 token**（无 token 拉 `.../logs` 会失败或被拒），
  所以脚本能看日志的那条路径要配 `GH_TOKEN`（可选，例如
  `$env:GH_TOKEN='xxx'; node --use-system-ca tools/gh-status.mjs`）；
- 但 **check-run 的 annotation 不需要 token**，就能读到失败原因的真实文本。
  所以**看失败原因优先看 annotation**，不要卡在「拉不到日志」上。

## 补充：子任务实测勘误与补充（请以本节为准）

### 勘误 1：CSS 里的鼠标指针**不会**坏

上一节曾把 `app/assets/css/main.css` 里的 10 条 `url('/cursors/...')` 列为项目站的风险项。**这是错的**，实测：

- 构建产物 `_nuxt/entry.*.css` 里实际写的是 `url(../cursors/normal-select.svg)`（**相对路径**）。
- 原因：Nuxt 通过 Vite 的 `renderBuiltUrl` 对非 JS 资源返回 `{ relative: true }`，所以 CSS 里的资源会自动重写成相对路径，**与 base 无关**。
- 结论：**鼠标指针在用户站和项目站下都正常**，不需要改。

### 勘误 2：漏了 3 处「整页跳转」的裸链接

`app/components/desktop/AboutWindow.vue` 里有 3 个裸 `<a href="/...">`（不是 `<NuxtLink>`），它们走的是**整页跳转**，项目站下同样会丢前缀：

- `AboutWindow.vue` 的 文章 / 标签 / 关于 三个链接

> 判据：`<NuxtLink>` 会自动带上 base，裸 `<a href="/...">` 不会。项目站下要全部换成 `<NuxtLink>` 或拼 `app.baseURL`。

### 补充 1：`__nuxt_content/blog/sql_dump.txt` 公开可下载

产物里有 `__nuxt_content/blog/sql_dump.txt`（gzip 压缩的内容库转储，约 12KB）。它是**客户端搜索（Spotlight）与 Finder 窗口查询文章所必需的**，删掉会让这两个功能失效。

风险：这个转储来自内容数据库，**很可能包含 `draft: true` 的草稿**。当前站没有草稿，所以暂无实际问题；以后写草稿要注意。

**推荐做法**：把草稿放在采集范围之外，例如 `content/drafts/xxx.md` —— 集合的 source 是 `blog/**/*.md`，`drafts/` 里的文件不会进集合，自然不会进转储。

### 待办提醒：换成本人信息

**个人身份信息集中在 `shared/site.ts` 一个文件里**：

```
name        站点名（标题栏 / 菜单栏 / RSS / llms.txt / 页脚）
author      作者昵称（首页名片、关于页）
avatarText  头像里显示的字
role        身份，例如「前端 / 全栈开发者」
tagline     首页名片上的一句话
bio         首页名片下的简介
about       关于页第一段
location    坐标
email       邮箱（关于页）
github      GitHub 地址（关于页）
socials     关于页的社交链接列表（邮箱 / GitHub 等）
description SEO 默认描述
keywords    首页 SEO 关键词
url         站点地址 —— 必须是真实的小写域名，它是 nuxt.config.ts 的兜底值（§5.2）
```

改完这个文件 **push 即自动重新部署**（push 到 main → `build` → `deploy`，约 2–4 分钟），
不需要碰工作流。改完记得按 §7.2 复检一遍 SEO 文件里的域名。

> **当前状态**：这个文件里除了 `url` 之外，其余字段**还是模板占位值**——
> 例如 `email: 'you@example.com'`、`github: 'github.com/yourname'`、`name: '我的博客'`、
> `author: '站长'`。这不影响部署能不能成功（站点能正常打开），但会在「关于我」页、
> 页脚、RSS 标题里露出占位文案。**换成本人信息只改这一个文件即可**，改完 push 就生效。
