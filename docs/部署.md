# 部署到 GitHub Pages

> 本文面向**第一次**把本站发到公网的人。全程约 10 分钟（其中 2–4 分钟是等 GitHub 构建）。
>
> 技术栈：Nuxt 4.5.2 + Nuxt Content 3.16 + Tailwind v4 + Pinia 4 + @nuxt/icon。
> 静态生成命令 `pnpm generate`，产物目录 `.output/public`。

---

## 0. 先理解三件事，再动手

1. **本项目是纯静态站点。** 在 GitHub Pages 上跑的是「构建时生成好的一堆 HTML/CSS/JS」，
   没有 Node 进程常驻。所有页面在 `pnpm generate` 时就被预渲染成文件：

   ```
   .output/public/
   ├─ index.html
   ├─ blog/index.html
   ├─ tags/index.html
   ├─ about/index.html
   ├─ sitemap.xml      ← 由 server/routes/sitemap.xml.ts 预渲染而成
   ├─ rss.xml          ← 由 server/routes/rss.xml.ts 预渲染而成
   ├─ robots.txt       ← 由 server/routes/robots.txt.ts 预渲染而成
   ├─ llms.txt         ← 由 server/routes/llms.txt.ts 预渲染而成
   ├─ _nuxt/           ← 打包后的 JS / CSS（注意下划线开头，很关键）
   └─ .nojekyll        ← 空文件，禁止 GitHub Pages 跑 Jekyll
   ```

   预渲染的路由清单写在 `nuxt.config.ts` 的 `nitro.prerender.routes` 里。

2. **评论系统在 GitHub Pages 上不可用，这是预期行为。** `/api/comments` 是 Nitro 服务端路由，
   需要 Node 常驻进程，静态托管拿不到。前端 `app/components/BlogComments.vue` 已经做了优雅降级：
   探测到接口 404/405 时显示「当前是**静态部署**（如 GitHub Pages），评论需要 Node 常驻服务，
   所以这里暂时不可用。」——**看到这段黄色提示不是 bug**，是想启用评论请换 Node 托管（见 §5.5）。

3. **工作流已经写好了，你基本不用改代码。** `.github/workflows/deploy.yml` 已经实现
   「推到 main → 自动构建 → 发布到 Pages」，§4 会逐段解释它。

## 1. 两条路线：用户站 vs 项目站（最容易踩坑的地方）

GitHub Pages 有两种站点形态，**仓库名决定了网址里有没有子路径**，而子路径会直接决定本站的
静态资源能不能加载。**第一次部署请直接选「用户站」。**

| 对比项 | **用户站（推荐）** | **项目站** |
| --- | --- | --- |
| 仓库名 | **必须是 `<你的用户名>.github.io`** | 任意，例如 `my-blog` |
| 访问网址 | `https://<用户名>.github.io/` | `https://<用户名>.github.io/my-blog/` |
| 站点根路径 | `/`（就是域名根） | `/my-blog/`（**有子路径**） |
| 本项目需要的改动 | **零改动**，`.github/workflows/deploy.yml` 直接就能用 | **需要额外处理绝对路径**，否则样式/图标/壁纸 404 |
| 每个账号能建几个 | 1 个 | 不限 |
| 适合 | 博客、个人主页的默认选择 | 一个账号放多个项目站，或不想占用那个特殊仓库名 |

### 1.1 用户站：零改动即可

仓库名叫 `<用户名>.github.io`，Pages 会把站点挂在域名根 `/` 上。
本项目所有以 `/` 开头的路径（`/cursors/...`、`/wallpapers/...`、`/app-icons/...`、`/rss.xml`）
**恰好都是对的**，不需要改任何代码。跟着 §2 走就行。

### 1.2 项目站：需要额外处理（重要）

如果仓库叫 `my-blog`，网址变成 `https://<用户名>.github.io/my-blog/`。
但本项目里有大量**以 `/` 开头的绝对路径**，它们会被浏览器解析成
`https://<用户名>.github.io/cursors/...`（**少了 `/my-blog`**），于是全部 404。
经核对，涉及以下位置：

| 位置 | 内容 | 后果 |
| --- | --- | --- |
| `app/assets/css/main.css:539-548` | `--system-cursor-*: url('/cursors/normal-select.svg')` 等 10 条鼠标指针 | 鼠标指针换不掉（不报错，但没效果） |
| `app/configs/wallpapers.ts:19-61` | `background: 'url("/wallpapers/big-sur-1.jpg") ...'` 等 8 张壁纸 | **桌面壁纸整块空白** |
| `app/configs/apps.ts:24-92` | `icon: '/app-icons/finder/128.png'` 等，以及 `to: '/rss.xml'` | Dock / 启动台图标全裂 |
| `app/components/desktop/LaunchpadOverlay.vue:76-89` | `src: '/app-icons/...'`、`to: '/rss.xml'`、`to: '/sitemap.xml'` | 启动台图标全裂、链接点错 |
| `app/layouts/default.vue:21-25` | `<a href="/sitemap.xml">`、`/llms.txt`、`/rss.xml` | 页脚链接 404 |
| `app/pages/index.vue:28-34` | 首页右上角 `/rss.xml`、`/llms.txt`、`/sitemap.xml` | 同上 |
| `app/components/desktop/AboutWindow.vue:48-50` | `/rss.xml`、`/sitemap.xml`、`/llms.txt` | 同上 |
| `app/components/desktop/FinderWindow.vue:140-142` | `window.open('/rss.xml')` 等 | 同上 |
| `app/components/desktop/TopBar.vue:299-315` | `openExternal('/rss.xml')` 等 | 同上 |
| `nuxt.config.ts:40` | `<link rel="alternate" ... href="/rss.xml">` | RSS 自动发现失效 |

**特别注意一个常见误解**：把 `NUXT_PUBLIC_SITE_URL` 设成
`https://<用户名>.github.io/my-blog` 只能修正 `sitemap.xml` / `rss.xml` / `llms.txt` 里
**写在文字里的绝对地址**，上面这些**静态资源请求**和**硬编码链接**它一个都修不好。

> 项目站的正确修法（设置 `app.baseURL`、改用 `useRuntimeConfig().app.baseURL` 拼接、
> 或把 public 资源引用改成相对路径）请见 **`docs/静态托管适配.md`**。
> 本文只负责「用户站零改动」这条路线。

## 2. 首次部署完整步骤（用户站路线，照做即可）

> 下文把 `<用户名>` 替换成你的 GitHub 用户名（区分大小写，用户名里的字母大小写按 GitHub 显示的写）。
> 示例：用户名是 `alice`，仓库名就是 `alice.github.io`，网址是 `https://alice.github.io/`。

### 步骤 1：在 GitHub 网页上新建仓库

1. 打开 <https://github.com/new>。
2. **Repository name** 填 **`<用户名>.github.io`**（例如 `alice.github.io`）。
   这是硬性要求——只有这个名字才会被识别成「用户站」，网址里才没有子路径。
3. **Description** 随便写，例如「我的个人博客」。
4. 可见性选 **Public**。
   （私有仓库在免费账号上不能发布 Pages，会卡在 Settings → Pages 里选不到 Source，所以选 Public。）
5. **下面三个复选框全部不要勾**：
   - ❌ Add a README file
   - ❌ Add .gitignore
   - ❌ Choose a license

   原因：本地 `my-blog` 已经是**有提交历史的 git 仓库**了。
   如果远端先有一个 README 提交，两边历史就没有共同祖先，第一次 `git push` 会被拒绝
   （见 §5.6）。
6. 点 **Create repository**。创建完会看到一个「…or push an existing repository from the command line」
   的页面，先用不上，直接看下一步。

### 步骤 2：本地关联远端并推送

在本机打开 PowerShell，执行（把两处 `<用户名>` 换掉）：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog

# 关联远端（本仓库当前没有配置任何 remote，git remote -v 是空的）
git remote add origin https://github.com/<用户名>/<用户名>.github.io.git

# 确认一下当前分支是 main（本仓库默认就是 main）
git branch --show-current

# 首次推送并把本地 main 与远端 main 建立跟踪关系
git push -u origin main
```

- 第一次推送会弹浏览器让你登录 GitHub（Git Credential Manager），或者要求输入 Personal Access Token。
  如果要求密码，**不能用账号密码**，要去 <https://github.com/settings/tokens> 生成一个带 `repo` 权限的
  token 当密码用。
- 如果提示 `error: remote origin already exists`，说明之前加过了，改成：
  ```powershell
  git remote set-url origin https://github.com/<用户名>/<用户名>.github.io.git
  ```
- 推送完成后仓库里应该能看到 `app/`、`content/`、`nuxt.config.ts`、`.github/` 等文件。
  注意 `node_modules/`、`.nuxt/`、`.output/`、`.data/`、`dist/` 已被 `.gitignore` 排除，**不会被推上去**，
  这是对的。

### 步骤 3：把 Pages 的来源切成 GitHub Actions

1. 打开仓库页面 → 上方 **Settings** 标签。
2. 左侧栏找到 **Pages**（在「Code and automation」分组下）。
3. **Build and deployment** → **Source** 下拉框，从 `Deploy from a branch` 改成 **`GitHub Actions`**。
4. 不需要选分支、不需要填目录。改完这一步就够了。
   （如果选成了 `Deploy from a branch`，Actions 里部署成功但 Pages 上仍然是空的——这是常见误操作。）

### 步骤 4：等 Actions 跑完

1. 点仓库上方 **Actions** 标签。
2. 左侧选 **Deploy to GitHub Pages** 工作流，点最新一次运行（触发器是 `push`）。
3. 你会看到**两个 job**：
   - **build**：安装依赖 → `pnpm generate` → 生成 `.nojekyll` → 上传产物。
     首次大约 **1.5–3 分钟**（要装 Nuxt 全套依赖 + 下载 better-sqlite3 预编译包）。
   - **deploy**：把上一步的 artifact 发到 Pages，大约 **20–40 秒**。
   合计 **约 2–4 分钟**。两个都变绿 ✅ 才算成功。
4. 如果 `build` 红了，点开失败的那一步看日志，对照 §5 的坑排查。

> 小提示：推送后如果 Actions 页面几秒钟内没出现新运行，刷新一下页面；
> 也可以在 Actions → Deploy to GitHub Pages → 右侧 **Run workflow** 手动触发一次（工作流里配了 `workflow_dispatch`）。

### 步骤 5：访问站点

浏览器打开：

```
https://<用户名>.github.io/
```

第一次发布后如果还是 404，**等 30–60 秒再刷新**（CDN 生效有延迟）。仍然 404 就回 §5 排查。

## 3. 以后怎么更新

写完文章、改完代码之后，三条命令推上去，剩下的 Actions 自动做：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog

git add -A
git commit -m "post: 新增《xxx》"
git push
```

- 只要推到 **main** 分支就会触发构建发布（`.github/workflows/deploy.yml` 里 `on.push.branches: [main]`）。
- 依赖有缓存，后续构建通常 **40–90 秒**。
- 推**其他分支**（如 `dev`）**不会**发布，也不会影响线上站点。
- 连推多次不会互相打架：工作流配了 `concurrency: group: pages, cancel-in-progress: true`，
  新的构建会取消还在跑的旧构建，最终只发布最新一次。
- 想只发一次而不改代码：Actions → Deploy to GitHub Pages → **Run workflow**（手动触发）。

## 4. `.github/workflows/deploy.yml` 逐段解释

文件全文 63 行，下面按段落拆开讲。

### 4.1 触发条件

```yaml
on:
  push:
    branches: [main]
  workflow_dispatch:
```

- `push.branches: [main]`：只有 **main** 分支收到推送才跑，其他分支不发布。
- `workflow_dispatch:`：允许在 Actions 页面**手动点按钮**触发一次（末尾的冒号不能省，
  空值表示「无参数的手动触发」）。

### 4.2 权限与并发

```yaml
permissions:
  contents: read     # checkout 读代码
  pages: write       # 允许写入 Pages
  id-token: write    # 允许用 OIDC 令牌向 Pages 证明身份（deploy-pages v4 必需）

concurrency:
  group: pages
  cancel-in-progress: true   # 新的发布取消旧的，避免两次部署打架
```

`id-token: write` 是**必须**的：`actions/deploy-pages@v4` 用 OIDC 换取发布凭证。
少了这一行，deploy job 会报权限类错误。`concurrency` 保证 Pages 同一时刻只有一个发布在跑。

### 4.3 build job

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
```

拉取仓库代码到构建机。

```yaml
      - uses: pnpm/action-setup@v4
        with:
          version: 10

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
```

- 装 **pnpm 10** 和 **Node 22**，与本项目要求一致。
- **顺序不能颠倒**：`setup-node` 的 `cache: pnpm` 依赖 pnpm 已经存在；
  如果先 setup-node 后 action-setup，这一步会报「找不到 pnpm 可执行文件」。

```yaml
      - uses: actions/configure-pages@v5
        id: pages
```

让 GitHub 把当前 Pages 站点的地址交给工作流，输出到 `steps.pages.outputs.base_url`。
用户站就是 `https://<用户名>.github.io`。**注意：这个 action 必须在 deploy 之前、且仓库已把
Source 切成 GitHub Actions 之后才拿得到正确地址**（§2 步骤 3 就是为它服务的）。

```yaml
      - name: Install dependencies
        run: pnpm install --no-frozen-lockfile
```

装依赖。两点说明：

- `--no-frozen-lockfile`：CI 默认会用 `--frozen-lockfile`，一旦 `pnpm-lock.yaml` 和
  `package.json` 有细微不一致就直接失败。这里放宽，允许按 `package.json` 修正锁文件。
- 这一步会顺带跑 `package.json` 里的 **`postinstall`**：
  `node scripts/install-sqlite-prebuild.mjs && nuxt prepare`。
  其中 `install-sqlite-prebuild.mjs` 负责补上 **better-sqlite3** 的预编译二进制
  （Nuxt Content 需要它）。为什么需要这个脚本：pnpm 10 默认**拦截**依赖的 install 脚本
  （`package.json` 的 `pnpm.onlyBuiltDependencies` 只放行了 `esbuild`），
  所以 better-sqlite3 不会自己下载/编译，必须由项目脚本补。
  详见 §5.3。

```yaml
      - name: Generate static site
        run: pnpm generate
        env:
          # sitemap / RSS / llms.txt 里的绝对地址
          NUXT_PUBLIC_SITE_URL: ${{ steps.pages.outputs.base_url }}
```

- `pnpm generate` = `nuxt generate`，按 `nuxt.config.ts` 里的
  `nitro.prerender.routes`（`/`、`/about`、`/blog`、`/tags`、`/rss.xml`、`/sitemap.xml`、`/llms.txt`、`/robots.txt`）
  加上所有文章页，生成纯静态文件到 `.output/public`。
- `NUXT_PUBLIC_SITE_URL` 覆盖 `nuxt.config.ts` 里 `runtimeConfig.public.siteUrl` 的默认值
  （默认是 `http://localhost:3000`）。`server/routes/sitemap.xml.ts`、`rss.xml.ts`、`llms.txt.ts`、
  `robots.txt.ts` 四个路由都读这个值来拼绝对地址。**这就是线上 sitemap/RSS 里不会是 localhost 的原因。**

```yaml
      - name: Disable Jekyll
        run: touch .output/public/.nojekyll
```

GitHub Pages 默认会跑 Jekyll 处理站点文件，而 **Jekyll 会忽略所有下划线开头的目录**，
包括 Nuxt 的 `_nuxt/`（里面全是 JS 和 CSS）。放一个空的 `.nojekyll` 文件即可关掉 Jekyll。
少了这一步的现象就是 §5.1：页面能打开但**样式全丢**。

```yaml
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .output/public
```

把 `.output/public` 整个目录打包成 Pages 专用 artifact。**路径必须是 `.output/public`**
（不是 `.output`，也不是 `dist`）。

### 4.4 deploy job

```yaml
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

- `needs: build`：build 失败就不会部署。
- `environment.name` **必须**是 `github-pages`，这是 GitHub Pages 的约定环境名；
  写错会导致发布被拒。
- `url` 会把线上地址显示在仓库首页右侧的 Deployments 里，方便直接点进去。
- `deploy-pages@v4` 消费上一步的 artifact 完成发布。它**不需要**再 checkout 代码，
  也不需要装 Node。

## 5. 常见坑（现象 / 原因 / 解决）

### 5.1 页面能打开，但样式和脚本全丢（白底黑字、布局塌掉）

**现象**：HTML 能出来，但 `https://<用户名>.github.io/_nuxt/xxx.js`、`_nuxt/xxx.css` 全是 **404**，
浏览器控制台一堆 404，页面没有任何样式。

**原因**：GitHub Pages 默认启用了 Jekyll，而 Jekyll 会跳过下划线开头的目录，`_nuxt/` 整个被吞掉。

**解决**：
- 走 Actions 工作流的话，**正常情况下不会出现**——工作流里已有
  `- name: Disable Jekyll / run: touch .output/public/.nojekyll`。
  先确认这一步确实执行成功了（Actions 日志里能看到）。
- 如果你是**手动**把 `.output/public` 上传/推到 Pages 分支，一定要自己造这个文件。
  Windows PowerShell 里 `touch` 不存在，用：
  ```powershell
  New-Item -ItemType File -Force .output\public\.nojekyll | Out-Null
  ```
- 顺手确认产物目录里确实有这个文件：
  ```powershell
  Test-Path .output\public\.nojekyll     # 期望输出 True
  ```
- 浏览器打开 `https://<用户名>.github.io/_nuxt/` 下任意一个真实文件 URL，能下载就说明修好了。

### 5.2 `sitemap.xml` / `rss.xml` 里还是 `http://localhost:3000`

**现象**：打开 `https://<用户名>.github.io/sitemap.xml`，里面 `<loc>` 是
`http://localhost:3000/...`；RSS 的 `<link>` 同理。搜索引擎会把这些地址当成站点地址，收录直接废掉。

**原因**：构建时没注入 `NUXT_PUBLIC_SITE_URL`，于是用了 `nuxt.config.ts` 里
`runtimeConfig.public.siteUrl` 的默认值 `'http://localhost:3000'`。

**解决**：
1. 确认 `.github/workflows/deploy.yml` 的 `Generate static site` 这一步带着：
   ```yaml
   env:
     NUXT_PUBLIC_SITE_URL: ${{ steps.pages.outputs.base_url }}
   ```
   这一行丢了是最常见的原因（尤其手抄工作流时）。
2. 确认仓库 Settings → Pages → Source 已经切成 **GitHub Actions**。
   没有这一步，`actions/configure-pages` 拿不到 `base_url`，注入进去可能是空值。
3. 改完后**重新触发一次构建**（重新 push，或 Actions 页面 Run workflow），
   本地改文件不算——Pages 上的文件是构建产物。
4. 有缓存的话强制刷新（Ctrl+F5）再检查。

> **另一个容易误会的点**：`shared/site.ts` 里的 `url: 'http://localhost:3000'` 字段，
> 注释虽然写着「sitemap / RSS 里的绝对地址」，但**当前代码里没有任何地方引用 `SITE.url`**——
> 四个 SEO 路由读的都是 `runtimeConfig.public.siteUrl`。
> 也就是说**只改 `shared/site.ts` 是没用的**，必须靠 `NUXT_PUBLIC_SITE_URL`。
> （想彻底避免混淆，可以顺手把 `shared/site.ts` 的 `url` 也改成真实域名，但它是纯装饰性的。）

### 5.3 Actions 里 `pnpm install` 失败在 better-sqlite3

**现象**：`Install dependencies` 这一步红了，日志里有
`[sqlite-prebuild] 所有镜像均下载失败。` 或者 `node-gyp` / `gyp ERR!` 之类的编译报错。

**原因**：Nuxt Content 依赖 **better-sqlite3**（原生模块）。它的正常安装需要下载预编译二进制或本地编译：

- pnpm 10 **默认拦截依赖的 install 脚本**，better-sqlite3 自己那套 `prebuild-install` 不会跑；
- 项目 `package.json` 的 `pnpm.onlyBuiltDependencies` 只放行了 `esbuild`；
- 所以本项目用 `scripts/install-sqlite-prebuild.mjs` 手动补二进制（挂在 `postinstall` 里）。

**解决**：
1. 打开 `scripts/install-sqlite-prebuild.mjs`，看第 35–40 行的**镜像列表**（按顺序尝试，第一个成功即停）：
   ```
   https://registry.npmmirror.com/-/binary/better-sqlite3/v<版本>/better-sqlite3-v<版本>-node-v<ABI>-linux-x64.tar.gz
   https://ghfast.top/https://github.com/WiseLibs/better-sqlite3/releases/download/v<版本>/<同上文件名>
   https://gh-proxy.com/https://github.com/WiseLibs/better-sqlite3/releases/download/v<版本>/<同上文件名>
   https://github.com/WiseLibs/better-sqlite3/releases/download/v<版本>/<同上文件名>
   ```
   四个全挂才会整体失败。日志里会逐个打印 `[sqlite-prebuild] 尝试：<url>` 和失败原因，看哪个报什么。
2. 注意脚本是**幂等**的：`node_modules/better-sqlite3/build/Release/better_sqlite3.node` 已存在就直接跳过。
   GitHub Actions 每次都是干净环境，所以 CI 上每次都会真下载；本地卡住时可以删掉那个 `.node` 文件重试。
3. 常见具体原因：
   - **文件名的 ABI / 平台对不上**：asset 名由 `process.versions.modules`（ABI）、
     `process.platform`、`process.arch` 拼出来。Actions 上是 Node 22 + linux + x64，
     而 npmmirror 上不一定每个版本都齐全 → 会自动落到 ghfast / gh-proxy 镜像，属正常。
   - **镜像临时不可用**：换个时间重跑（Actions 页面 → 失败运行右上角 **Re-run failed jobs**），
     或者临时把可用的镜像 URL 提到 `mirrors` 数组第一位。
   - **升级了 better-sqlite3 版本**：确认 `pnpm-lock.yaml` 和 `package.json` 里的版本一致，
     否则拼出来的文件名在镜像上不存在。
4. **兜底方案**（脚本自己也会提示）：手动下载那个 `better-sqlite3-v<版本>-node-v<ABI>-linux-x64.tar.gz`，
   解压后把里面的 `build/Release/better_sqlite3.node` 放到
   `node_modules/better-sqlite3/build/Release/` 下。
   ⚠️ 注意 CI 是 Linux，本地 Windows 下好的是 `win32-x64` 的版本，
   **两者不能互换**，也不要把本地的 `.node` 提交进仓库。
5. 想彻底绕开这个原生依赖，只能不用 Nuxt Content 的 SQLite 后端（代价很大），
   本项目不建议走这条路。

### 5.4 图片 / 壁纸 / Dock 图标 404（项目站专属）

**现象**：页面结构正确，但桌面背景是纯色、Dock 和启动台图标是裂图，
控制台是 `https://<用户名>.github.io/wallpapers/big-sur-1.jpg 404`（注意**没有** `/my-blog` 这一段）。

**原因**：仓库名不是 `<用户名>.github.io`，站点被挂在子路径 `/my-blog/` 下，
而本站 CSS 和组件里用的是以 `/` 开头的**根路径绝对地址**。清单见 §1.2 的表格。

**解决**：
1. **最省事的办法**：这条路线别用，改建成用户站（仓库名 `<用户名>.github.io`），零改动。
2. 真要发布项目站，按 `docs/静态托管适配.md` 处理：
   给 Nuxt 设置 `app.baseURL`，并把 `app/assets/css/main.css`、`app/configs/wallpapers.ts`、
   `app/configs/apps.ts`、`app/components/desktop/LaunchpadOverlay.vue`、
   `app/layouts/default.vue`、`app/pages/index.vue`、`app/components/desktop/AboutWindow.vue`、
   `app/components/desktop/FinderWindow.vue`、`app/components/desktop/TopBar.vue`
   里那些 `/...` 硬编码统一改成基于 baseURL 的写法。
3. 提醒：**光把 `NUXT_PUBLIC_SITE_URL` 改成带 `/my-blog` 的地址是不够的**，
   它只影响 sitemap/RSS/llms.txt 的文本内容，修不了资源请求。

### 5.5 评论区显示「当前是静态部署…」

**现象**：文章页底部有一块黄色提示：
「当前是**静态部署**（如 GitHub Pages），评论需要 Node 常驻服务，所以这里暂时不可用。」

**原因**：**这是预期行为，不是 bug。** 评论功能由 `server/api/comments/*`（GET / POST / DELETE）
提供，还依赖 `server/utils/comments-db.ts` 里的 SQLite 数据库文件，必须有 Node 进程常驻才能工作。
GitHub Pages 只能托管静态文件，`/api/comments` 请求会返回 404/405，
`app/components/BlogComments.vue` 捕获到这个状态后就把表单换成说明文案（`apiUnavailable` 分支）。

**解决**：
- 接受它（博客本身完全可用），或者
- 想启用评论就换成**支持 Node 运行时的托管**，例如 Cloudflare Workers/Pages Functions、Vercel、
  Netlify Functions、Railway、或者自己的 VPS。
  这条路要改的是「部署形态」而不是本文的 Pages 流程：不再跑 `pnpm generate`，
  而是跑 `pnpm build` 并保留 `.output/server`，同时注意 SQLite 文件需要**持久磁盘**
  （多数 Serverless 平台的临时文件系统会在实例重启后丢掉评论数据，需要挂载卷或换用外部数据库）。
  具体 API 设计见 `docs/评论系统.md`。
- **不要**为了消除这块提示去删组件代码，否则以后想换托管时还得写回来。

### 5.6 `git push` 被拒绝（rejected / 无共同祖先）

**现象**：第一次推送时出现下面这类报错：

```
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/<用户名>/<用户名>.github.io.git'
hint: Updates were rejected because the remote contains work that you do not have locally.
```

或者：

```
fatal: refusing to merge unrelated histories
```

**原因**：建仓库时勾了 **Add a README file**（或 .gitignore / license），
GitHub 先建了一个提交，远端有了本地没有的历史；
而本地 `my-blog` 是独立初始化的仓库，两边没有共同祖先。

**解决**（按推荐顺序）：

1. **推荐：把远端的历史接上来，再推**——先拉取并用 rebase 把本地提交放到远端提交之后：
   ```powershell
   git pull --rebase origin main
   git push -u origin main
   ```
   因为两边改的文件基本不重叠（远端只有一个 README），一般不会冲突。
2. **如果 `git pull --rebase` 报 `refusing to merge unrelated histories`**：
   ```powershell
   git pull --rebase origin main --allow-unrelated-histories
   git push -u origin main
   ```
3. **如果只是「远端被别处改过、本地落后」**（比如在另一台电脑推过），
   同上，先 `git pull --rebase origin main` 再 `git push`，**不要**用 `-f`。
4. **最后的办法：强推覆盖远端**——只有在你**确定远端那些提交毫无价值**时才用：
   ```powershell
   git push -f origin main
   ```
   ⚠️ **风险很大**：`-f` 会**永久丢弃远端上本地没有的提交**，无法通过普通 `git pull` 找回
   （只能在 GitHub 的 Activity / 悬空提交里碰运气）。如果那个仓库里已经有别人推的东西、
   或者你已经在网页上改过文件，**不要用 `-f`**。
   更安全的做法是去 GitHub 网页把那个多余的 README 删掉（删文件提交），再 `git push`。

## 6. 自定义域名（可选）

已经有域名（例如 `blog.example.com`）的话，可以不用 `*.github.io` 地址。

### 6.1 在项目里加 CNAME 文件

Nuxt 会把 `public/` 目录下的内容**原样拷到产物根目录**，所以文件放这里：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog
Set-Content -Path public\CNAME -Value 'blog.example.com' -NoNewline
```

- 内容就是**裸域名**，一行，不要写 `https://`、不要写路径、结尾不要有多余空行。
- 该文件必须进 Git（`public/` 没被 `.gitignore` 排除）：
  ```powershell
  git add public/CNAME
  git commit -m "chore: 添加自定义域名 CNAME"
  git push
  ```
- 为什么用 `public/CNAME` 而不是在 Pages 设置里让 GitHub 自动写：走 **Actions 发布**时，
  artifact 里是什么就发布什么；GitHub 自动建的那份 CNAME 不一定能保住。放进仓库最可靠。

### 6.2 在 GitHub 上填自定义域名

1. 仓库 → **Settings** → **Pages** → **Custom domain** 填 `blog.example.com` → **Save**。
2. GitHub 会做一次 DNS 检查。刚加完报「DNS check unsuccessful」是正常的，
   等 DNS 生效（几分钟到几小时）后回来点 **Check again**。
3. 等证书签发完成后，勾上 **Enforce HTTPS**（强制 HTTPS）。证书签发可能要几分钟到几小时。

### 6.3 在域名商那里加 DNS 记录

| 你要用的域名 | 记录类型 | 主机名 / 名称 | 值 |
| --- | --- | --- | --- |
| 子域名，如 `blog.example.com` | **CNAME** | `blog` | `<用户名>.github.io` |
| 裸域名（apex），如 `example.com` | **A** | `@` | `185.199.108.153`<br>`185.199.109.153`<br>`185.199.110.153`<br>`185.199.111.153` |

- CNAME 的值**不要**带 `https://`，也**不要**带仓库名，最后不要加 `.`（多数面板会自动补）。
- 裸域名用 A 记录是 GitHub Pages 的官方做法；如果你的域名商支持 `ALIAS` / `ANAME`，
  也可以指向 `<用户名>.github.io`。**具体 IP 以 GitHub 官方文档为准**，
  它们偶尔会调整，部署前建议核对一遍。
- DNS 改完可以用下面命令确认解析是否生效：
  ```powershell
  Resolve-DnsName blog.example.com -Type CNAME
  ```

### 6.4 把 `NUXT_PUBLIC_SITE_URL` 改成自定义域名

**这一步不做的话，sitemap / RSS / llms.txt 里仍然是 `*.github.io` 地址**，
和实际访问的域名不一致，对 SEO 不利。

在 `.github/workflows/deploy.yml` 的 `Generate static site` 步骤里改成硬编码：

```yaml
      - name: Generate static site
        run: pnpm generate
        env:
          NUXT_PUBLIC_SITE_URL: https://blog.example.com
```

说明：
- **不要**写成 `https://blog.example.com/`（结尾带斜杠）。四个 SEO 路由里有
  `.replace(/\/$/, '')` 处理，多一个斜杠通常不会出错，但统一不带斜杠更稳。
- 理论上 `actions/configure-pages` 在设置了 Custom domain 之后会输出自定义域名，
  但为了不依赖它的推断行为，**配置了自定义域名就建议直接硬编码**，最省心。
- 改完 push 一次，等 Actions 跑完，再按 §7 复检 sitemap/RSS。
- 换域名后，搜索引擎那边等于一个新站点，需要**在 Google Search Console 里重新添加并提交 sitemap**（见 §7）。

- [ ] `/tags` 标签页能打开

- [ ] **直接粘贴某篇文章的完整 URL 到新标签页打开**（不是从首页点进去），
      刷新也不 404 —— 说明预渲染覆盖到了文章级路由
- [ ] 浏览器控制台（F12 → Console）**没有 404 报错**
- [ ] 深色模式切换、字号设置能生效（用的是 localStorage，无后端依赖）
- [ ] 文章页评论区显示「当前是静态部署…」的黄色提示 = **预期行为，正常**

### 7.2 SEO 文件里的域名是不是真的

四个文件都应该是**真实域名**，不能出现 `localhost`：

- [ ] `https://<用户名>.github.io/sitemap.xml` —— 能直接打开，`<loc>` 全是真实域名，
      且包含你的文章 URL
- [ ] `https://<用户名>.github.io/rss.xml` —— 能直接打开，`<link>` 是真实域名，
      有文章条目
- [ ] `https://<用户名>.github.io/robots.txt` —— 能打开，里面的 Sitemap 行是真实域名
- [ ] `https://<用户名>.github.io/llms.txt` —— 能打开，站名/地址正确

命令行快速检查（把 `<用户名>` 换掉）：

```powershell
$u = 'https://<用户名>.github.io'

# 抓 sitemap，看看里面有没有 localhost（期望：没有任何输出）
(Invoke-WebRequest "$u/sitemap.xml").Content -split "`n" | Select-String 'localhost'

# 看 sitemap 前几行，确认真实域名
(Invoke-WebRequest "$u/sitemap.xml").Content -split "`n" | Select-Object -First 8

# 看 rss 里的站点链接
(Invoke-WebRequest "$u/rss.xml").Content -split "`n" | Select-String '<link>'
```

> ⚠️ 如果这台机器的 hosts 把 `github.com` 之类指向了 `127.0.0.1`（本机确实有这种配置），
> PowerShell 的 `Invoke-WebRequest` 有可能连不上；这时改用浏览器打开，
> 或者用手机 / 另一台机器验证，不要以为站点坏了。

还有一个更省事的办法——仓库里已经带了验收脚本 `tools/verify.mjs`，可以直接对着线上地址跑：

```powershell
cd E:\AIStudy\AIProjects\factory\WorkLog\Work0909\Work09098\my-blog
node tools/verify.mjs --base https://<用户名>.github.io --skip-comments
```

它会检查 `/`、`/blog`、`/tags`、`/about`、`/sitemap.xml`、`/rss.xml`、`/llms.txt`、`/robots.txt`
以及真实 App 图标是否可用（`--skip-comments` 是因为静态托管上评论接口本来就不存在，
不跳过的话那一组会失败）。退出码 0 = 全部通过。

### 7.3 提交给搜索引擎

- [ ] 打开 <https://search.google.com/search-console> → **添加资源**
- [ ] 因为用的是 `*.github.io` 域名，选 **「网址前缀」** 方式，填
      `https://<用户名>.github.io/`（**注意结尾的 `/`**）
- [ ] 验证所有权：GitHub Pages 站点无法方便地上传 HTML 验证文件到根目录，
      优先用 **Google Analytics / Google Tag Manager** 或 **DNS 验证**（有自定义域名时）；
      最简单的替代是用 **Bing Webmaster Tools**，它支持导入 GSC 资源
- [ ] 验证通过后 → 左侧 **Sitemaps** → 提交 `sitemap.xml`（相对路径即可）
- [ ] 状态变成 **Success**，且「已发现的网页」数量与文章数对得上
- [ ] 用顶部 **网址检查** 工具输入一篇文章 URL，确认「网址可编入索引」
- [ ] （可选）同样在 <https://www.bing.com/webmasters> 提交一次，Bing 收录通常更快
- [ ] （可选）更新 `shared/site.ts` 里的 `url` 字段为真实域名，消除文档层面的歧义
      （它对构建没有实际影响，见 §5.2 的提示）
