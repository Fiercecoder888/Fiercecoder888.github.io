## 今天做了什么

上午把工作日志四个入口的验证彻底收到线上。本地 10 条验收命令全绿（两道守卫、资源 67/67、`verify` 25/0、`e2e` 54/0、`qa` 浅色/深色/390×844/700×900 四档 0 error 0 warn、光标巡检 12 处）；两条自动化断不到的交互承诺用真浏览器补验 —— ⌘K 搜一个只在某天 frontmatter 里出现过的词、Finder 里点一行关窗跳转、终端 `log 2` 与 `log 09-17` 分别打开对应的两天。随后 3 次追加提交，CI 三次部署全 success，线上复核 5/5。

下午转到另一个业务仓库，把远端集成分支合进正在用的工作副本。两边都往前走了：远端比本地早 7 个提交，本地比它多 43 个。合并结果 **4 个文件 / 7 处冲突**，全部解决后提交并留了备份分支。冲突处置都不是二选一，而是合成：后端「特例排在登记表之前、其余仍走注册表」，前端「属性与渲染链两边都留、注释合成一份、侧栏两项都留」，迁移 README 采用远端的编号说明。

合完跑了四层验证：Python 语法编译 → TypeScript 类型检查 → oxlint（0 警告 0 错误）→ 前端测试（2 通过，正是远端这次带进来的那两条生命周期钉子）。中途还补装了一个远端声明新增、本地却没装的依赖 —— 补装前测试是红的，红的原因是「模块找不到」，不是功能坏了。

## 两条最值得记下来的

**线上复核带了「上线前」对照。** 同一个脚本在新版上线**前**跑是 4 通过 / 1 失败（失败项正是新出口的钩子），上线**后**才 5/5。如果没有这次前后对照，「5/5 全绿」只能说明脚本没报错，说明不了改动真的生效 —— 这是今天最值得留档的一条方法学证据，也是以后做线上校验的默认姿势。

**合并的难点不在文本冲突，而在语义。** 这次最费神的一处，是两边对同一个函数做了不同的结构性改造（一边重构成表驱动，一边加特例）——git 只会把它们标成一处普通冲突，真正的工作是判断「谁在前谁在后」。而 git 完全不报的地方也可能已经错了（同号不同名的迁移文件、被改成位置参数的调用点），所以合完必须跑验证，且从便宜的验证开始跑。
