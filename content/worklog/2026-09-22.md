今天做的事，一句话就能说完：让博客上那个决策台从「假能用」变成真能用。

它之前的状态很有欺骗性——界面在、按钮在、点下去也有反馈，只是那句提示是「本地 pnpm dev 可用」。也就是说除了我自己这台开着 dev server 的机器，谁点都得不到结果。这种「看着做完了」的东西比明显没做的更麻烦，因为它连自己没做完都藏起来了。接上真实后端的改动其实不大：浏览器只打同源接口，key 只活在服务端的平台变量里。真正花时间的是选那个「服务端」放在哪。

这一步是纯实测。Deno Deploy 域名通、注册被服务端拒，社区反馈免费用户现在要绑卡；Cloudflare Workers 和 Vercel 注册页能打开，可运行时域名被 DNS 投毒——随机子域解析到几家大厂的 IP，注册成功也打不开；Render 和 Koyeb 能用，但免费实例闲置十五分钟后首个请求要冷启动将近一分钟。对别的项目这一分钟可能无所谓，对一个「控制台」来说它就是「点了没反应」。最后落在 Netlify：函数不睡、域名可达、404 是真实响应。整件事让我把「选平台」重新归类了一道——它是实测题，不是印象题，而且判据应该是「对我这个用途最坏的那一条」，不是各家的功能列表。

下午在界面上改了三处。原来置信度是裸的 `置信 0.37`，现在写成「把握 37% · 存疑 · 建议人工确认」——裸数字要读者自己知道 0.37 算高还是低，三档分界线其实就是「自动处置 / 需要留意 / 该转人工」。每张结果卡还加了一句人话的结论，因为只显示一个 `technical` 等于没说。

三处里最值得记的是第三处，它是个真踩过的坑：改了输入却没重新点运行，屏幕上还摆着上一次的答案，看上去完全就是当前输入的结论。当时是靠 token 数反推出来的——输入改了而 tokens 没变，说明发出去的不是屏幕上那份。修的方式不是「输入变了就清空结果」，而是把过期判据锚在**点运行那一刻的快照**：请求发出之后用户还会继续打字，那份结果对应的仍然是发出时的输入。

还有一个被用户一句话点破的地方。有人反馈「看不到」，界面上只有一个孤零零的 0.45——我问的是「这句话有没有表达紧迫」。第一反应是 criteria 写错了，连着跑六次，结果稳定在 0.89~0.90，跨度 0.01，数值明明很稳。真正的原因是我用错了问题类型：那种类型天生只返回一个 0~1 的数，没有分布也没有把握度，屏幕上当然只剩一个数字。换成一组选择题（意图、紧迫度、情绪、下一步）之后，一次就能拿到「结论 + 把握度 + 分布 + 下一步」。顺带验出一个反直觉的事实：题目和判据用英文写、聊天内容保持中文原文，分数才稳——用中文写题会把置信度从 0.99 拉到 0.84，分数还会系统性上漂约 0.10。

今天最后收在一句话上：给读者一个数字之前，先给他判断这个数字该不该信的依据。下次接后端，顺序也固定了——先把「这台机器之外能不能用」问清楚，再挑平台，最后才动界面。
