## 今天做了什么

先把一个后端仓库拉到本地跑起来（虚拟环境、依赖、临时环境文件、健康检查都通了），再把一份新前端接到它上面做联调，并拆了一批并行子任务：前端代理指向本地后端、浏览器级端到端验收、给流水线接模型能力并配可重复执行的验证脚本。

踩到的问题集中在四件事：Windows 编码、模型与人工确认的边界、验收失败的归因，以及交付版本拿错。

## 踩的坑与解决

**Windows 上 Python 读不了 UTF-8 清单文件**
跑测试时前面全过，到读某个 UTF-8 的清单文件就失败——Python 默认按系统本地编码（cp936）去读，内容一解码就崩。设 `PYTHONUTF8=1` 再重跑立刻通过。凡是 Windows 上读文本文件的脚本和测试，先把编码钉死（环境变量或显式指定 `encoding`），别依赖系统本地编码。

**差点让模型把人工确认环节架空**
给一条多阶段流水线里的若干阶段接模型能力，其中一个人工确认环节的触发条件是「某个字段为空」。如果让模型直接把那个字段写进结果，人工确认就永远不会触发——流程看着「跑通了」，实际上没人在审核。改法是把模型输出限制成「建议」：只写进建议字段，驱动人工确认的字段保持为空，由人和确定性代码去填。整个改造还要做成开关式包装：关掉开关行为必须和改造前完全一致，打开才真的走模型，两种状态都要有测试证明。

**验收失败不是环境问题，是业务前置数据**
联调时验收脚本断言失败，第一反应是「服务没起来 / 端口不对 / DNS 有问题」。实际服务健康、端口在听、健康检查返回 200，是业务流程跑到某个阶段被输入校验拦下了（返回 `BLOCKED_INPUT`）。做法是先把环境层和业务层分开看：确认服务健康、端口在听、接口能返回 200，再去查流程在哪一步被拦、拦它的那条校验需要什么前置输入。归因错了就会去修根本没坏的东西。

**按「最新的那份」交付，版本是错的**
对方要的是「加某批新模块之前」的那一版前端，而手边并存的副本有好几份，按「最新的那份」打包发出去，里面已经带上了后来才加的模块，只能重来。交付前要用可核对的硬特征确认版本（某个模块或路由在不在、某次提交在不在），别用「最新的那份」这种说法指代版本；多份副本并存时，给每一份标清它对应哪一批需求。

## 今天学到

- Windows 上读文本文件先钉死编码：Python 直接给 `PYTHONUTF8=1`，别依赖系统本地编码（cp936）。
- 给老代码加「可开关」的包装层时不要改函数名与参数签名：直接 import 调用它的现有测试会立刻红。
- 模型只能「提议」不能「写入」：凡是被人工确认环节当作触发条件的字段，模型一个都不许写。
- 只起了前端没起后端时页面照样能打开，「页面能打开」不能当联调环境就绪的判据。
- 为了本地跑通临时补的桩接口要显式标记，否则会被当成「功能已实现」。
- 验收失败先分清环境层和业务层：服务健康、端口在听，再去看流程被哪条输入校验拦住。
- 密钥只放在本地未提交的环境文件里，不进仓库。
