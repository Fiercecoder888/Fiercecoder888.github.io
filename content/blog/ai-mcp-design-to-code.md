## 那篇文章讲了什么

作者的场景很典型：产品丢来一张设计图，让做一个官网静态页。他的第一反应是"要不要做 SEO""用原生还是框架"，结果组长一句话跳过所有选型——**下载蓝湖 MCP，直接原图直出**。

结果：下午四点接活，四点四十做完，其中三十分钟在装环境。

## 蓝湖 MCP 到底做了什么

它本质是一个 [Model Context Protocol](https://modelcontextprotocol.io/) 服务器，把设计协作平台的能力暴露给 AI 编码工具（Cursor、Claude Code、Trae 等）：

- 读取需求文档（含 Axure 原型）
- 读取设计稿，提取尺寸 / 间距 / 颜色 / 字体
- 下载切图，语义化命名
- 输出一份 HTML + CSS 参考代码

也就是说，AI 不再靠"猜"设计图长什么样，而是拿到了结构化的设计参数。**这才是它比"截图给 AI 看"强的地方。**

## 但要泼一盆冷水

社区里也有不少踩坑记录：能装、能跑，但真正用起来受限于设计稿的规范性、账号权限、切图资源质量。设计图比例不对、组件复用混乱的项目，出码质量会掉得很快。

更现实的问题是：**生成的代码通常只能"看起来对"**。命名、状态管理、响应式断点、无障碍、性能预算——这些它不管，最后还得人来收拾。

## 我的判断

AI 把"切图"这件事的边际成本压到了接近零，这是事实。但前端真正值钱的部分一直不在切图上：

| 会贬值 | 会升值 |
| --- | --- |
| 手写 CSS 还原视觉 | 判断这个页面该不该存在 |
| 按稿实现交互 | 拆解需求、定接口、定边界 |
| 重复的 CRUD 页面 | 排查"线上偶发白屏"这类问题 |
| 记住某个 API 的写法 | 技术选型的取舍与兜底 |

作者文章结尾那句挺真实：**"我能想到的是：AI 能还原 UI，但它不知道为什么要这么做。"**

## 结论

- 有设计稿、要快速出静态页 → MCP 直出确实能省一大截时间，值得试；
- 复杂业务、长期维护的项目 → 别指望它替你做完，把它当成"高级脚手架"更合适；
- 对个人来说，与其焦虑"会不会被替代"，不如把时间花在**决策能力**和**排障能力**上。
